# LLM 基础概念与 RAG 完整链路

> 来源：豆包会话第 1、2 轮，归纳整理并修正 token 估算口径（见文末勘误注）。
> RAG 是 AI 应用方向面试**最高频**模块，务必能脱稿讲完整链路 + 每个环节的工程取舍。

## 一、大模型基础概念（浅度，够用即可）

### 1. 什么是 LLM

大语言模型：基于 **Transformer 架构 + 注意力机制**训练的超大规模语言模型，核心能力是长文本理解与生成。面试一句话：

> Transformer 的注意力机制让模型在处理每个词时都能「看到」上下文所有词并分配权重，所以它理解的是全局语义，不是一个词一个词孤立地看。

不需要讲 self-attention 公式，讲清楚 Q/K/V 的直观含义即可（被问到再展开）。

### 2. Token 与计费

- **Token 是模型处理文本的最小单位**，输入 + 输出都计费（很多平台输入、输出单价不同，输出更贵）
- **中文比例因分词器而异**：
  - 老分词器（cl100k_base，GPT-3.5/4 时代）：约 0.5~0.7 个汉字 / token（即 1 汉字 ≈ 1.4~2 token）
  - 新分词器（GPT-4o 的 o200k、Qwen、DeepSeek 等）：中文压缩率显著提升，约 1~1.8 个汉字 / token
- 工程口径：**成本测算不要背通用常数，用目标模型的 tokenizer 实测**；代码里对输入做 `estimateTokens()` 预估并计入限流额度

> ⚠️ 勘误注：原笔记写「中文约 1 token ≈ 1.5~2 汉字」，这个数字只在老分词器下大致成立，新模型下偏高。面试安全说法：「因模型而异，粗估 1~2 汉字一个 token，我们会按所用模型实测后再做成本预算」。

### 3. Prompt / Few-shot / Zero-shot / CoT

| 概念 | 含义 | 用途 |
| --- | --- | --- |
| Prompt | 给模型的输入指令 | 控制输出风格、格式、边界 |
| Zero-shot | 不给示例直接问 | 简单任务 |
| Few-shot | 给少量输入输出示例 | 固定输出格式时最有效 |
| CoT（思维链） | 引导模型「分步推理再回答」 | 复杂推理任务，减少跳步错误 |

### 4. 上下文窗口（Context Window）

模型单次能「看到」的 token 上限（如 8K / 32K / 128K）。超出就要**截断、摘要压缩或检索替代**——这是多轮对话管理的根源问题，工程方案见 `ai-05-java-engineering.md`。

### 5. Embedding 模型 vs 生成模型

| | Embedding 模型 | 生成模型（LLM） |
| --- | --- | --- |
| 输入 | 文本 | prompt |
| 输出 | 固定长度向量 | 自然语言 |
| 用途 | 语义检索、聚类、去重 | 理解、生成、推理 |
| 计费 | 按 token 计费但单价低 | 单价高 |

### 6. 公有云 API vs 私有化部署

| 维度 | 公有 API | 私有化部署 |
| --- | --- | --- |
| 接入速度 | 快 | 慢（GPU 采购/推理服务搭建） |
| 运维 | 轻 | 重 |
| 数据安全 | 数据出内网（有合规风险） | 数据不出内网 |
| 延迟 | 受网络和供应商限流影响 | 可控 |
| 模型更新 | 跟供应商走 | 自己升级 |

选型口径：**内部敏感数据 / 强合规场景选私有化；一般业务用公有 API + 脱敏**。

## 二、RAG 检索增强生成（最高频）

### 1. 为什么需要 RAG

LLM 三个天然缺陷：**知识滞后**（训练截止日期后的不知道）、**无私有数据**（企业内部文档没见过）、**幻觉**（不知道也编）。RAG 用「先检索、再生成」解决这三个问题，同时比微调便宜得多、更新快得多。

### 2. 完整链路（必须脱稿）

```
【离线索引】文档加载 → 清洗 → Chunk 分片 → Embedding 向量化 → 存入向量库
【在线问答】用户 query → Embedding → 向量相似度召回 TopN →（可选 Rerank 重排）
           → 检索片段拼入 prompt → LLM 生成（引用原文、无关则拒答）
```

### 3. Chunk 分片策略

- **过大**：一个片段里塞了太多主题，向量被「平均」，相似度下降，且拼 prompt 浪费 token
- **过小**：语义不完整，召回了半句话没法用
- **overlap（重叠窗口）**：相邻片段保留重叠文本，防止一句话的语义正好被切断在边界上
- 经验值：通用文档 500 字符 + 100 overlap 起步，**按文档类型调**（表格/代码/法律条文各自不同）；结构化文档优先按标题/段落切，不硬按字数切

### 4. 向量检索原理（不講公式版）

文本经 Embedding 模型转成固定长度向量，**语义相近的文本在向量空间里距离近**。检索时把 query 也转成向量，用**余弦相似度**（看夹角，不受向量长度影响）算距离，取最近的 TopN。向量库底层用近似最近邻（ANN，如 HNSW）索引实现毫秒级召回。

### 5. 向量库选型

| 选 | 场景 | 理由 |
| --- | --- | --- |
| PgVector | 数据量百万级以内、已有 PG | 复用现有数据库，零新增中间件运维 |
| Milvus | 海量文档、高 QPS | 分布式架构、HNSW/IVF 多种索引 |
| Chroma | 原型验证 | 极轻量 |
| ES 8.x 向量 | 已有 ES、要混合检索（关键词+向量） | 一套引擎两路召回 |

### 6. RAG 常见问题与工程优化

| 问题 | 优化手段 |
| --- | --- |
| 检索到无关文档 | 相似度阈值过滤 + Rerank + 元数据过滤（时间/部门/权限） |
| 幻觉 | prompt 强约束「只基于给定片段回答」+ 引用原文标记 + 无相关信息拒绝回答 |
| 召回不准 | 改写 query（同义扩展）、混合检索（BM25 + 向量）、调 Chunk 策略 |
| 多轮指代不清 | 对话历史补全 query（"它多少钱"→"卡罗拉多少钱"）再检索 |

### 7. Rerank 重排

召回阶段为了快用的是双塔向量模型（粗排）；Rerank 用交叉编码器对 query+文档**逐对精细打分**（精排），准确率明显提升但耗时增加。策略：**召回 Top50 → Rerank 取 Top5 → 拼入 prompt**，按成本预算决定要不要开。

### 8. RAG vs 微调（必考对比）

| 维度 | RAG | 微调 |
| --- | --- | --- |
| 适合 | 知识频繁更新、私有知识库 | 固定输出风格/格式/领域语感 |
| 更新成本 | 改文档重新向量化即可，分钟级 | 重新训练，天级 + 花钱 |
| 可解释性 | 能给出来源引用 | 黑盒 |
| 硬件成本 | 只需向量库和检索服务 | 需要 GPU 训练资源 |
| 结合 | 生产上常组合：微调管「怎么说」，RAG 管「说什么」 | |

### 9. 向量库与业务库同步

- 业务库存文档元数据和原文，向量库只存分片向量 + chunk_id 映射
- 文档**增改**：重新切片 → 重新向量化 → 按 doc_id 增量更新（不全量重建）
- 文档**删除**：软删除标记，检索时过滤；物理删除时同步删向量
- 用 binlog / 消息队列驱动异步同步，失败重试

## 追问链 · 参考答案

| 层级 | 问题 | 参考答案要点 |
| --- | --- | --- |
| L1 | RAG 的完整链路有哪几步？Chunk 为什么不能太大也不能太小？ | 链路：离线侧文档加载 → 清洗 → Chunk → Embedding → 入向量库；在线侧 query Embedding → 相似度召回 TopN → 可选 Rerank → 拼 prompt → LLM 生成。Chunk 过大会让向量被多主题「平均」、相似度下降还浪费 token；过小语义不完整、召回半句没法用，所以取 500 字符 + 100 overlap 起步并按文档类型调。 |
| L2 | 为什么选 PgVector 不选 Milvus？overlap 到底解决什么问题？ | PgVector 复用现有 PostgreSQL，零新增中间件运维，百万级以内完全够用；Milvus 是分布式专用库，适合海量文档高 QPS，但运维成本高，接口层做抽象将来再迁。overlap 解决的是「一句话的语义正好被切断在分片边界」——相邻片段保留重叠文本，保证边界处的语义完整可召回。 |
| L3 | 幻觉的四个工程手段分别作用在哪一层？ | 检索层：相似度阈值过滤 + 元数据过滤，先挡住无关片段；prompt 层：强约束「只基于给定片段回答」+ 要求引用原文标记，把模型钉在证据上；业务层：无相关信息时拒绝回答，宁可不答不编。工程上还可以加内容审核兜底，四层组合拳而不是指望单点解决。 |
| L4 | 召回率上不去，你的排查顺序是什么？ | 先看 query 侧：多轮指代有没有改写补全、要不要同义扩展或混合检索（BM25+向量）；再看 Chunk 策略：是不是切碎了语义、要不要按标题切或调 overlap；然后怀疑 Embedding 模型本身：领域词区分度低就换领域模型；最后才加 Rerank 精排。按从便宜到贵的顺序排，别一上来就换模型。 |
| L5 | 文档更新是实时的吗？同步链路挂了怎么办？ | 不是强实时，是 binlog/MQ 驱动的异步增量同步：文档增改重新切片向量化按 doc_id 更新，删除打软删除标记检索时过滤。链路挂了靠两层兜底：MQ 失败重试，再加一个定时对账任务比对业务库和向量库差异补齐，保证最终一致，不做全量重建。 |

## 误区 · 正解

| ❌ 误区 | ✅ 正解 |
| --- | --- |
| ❌ RAG 就是接个向量库 | 接向量库只是最省力的一步，真正的工程量在前后两端：分片策略决定召回质量（按结构切、加 overlap）、同步链路保证数据新鲜（MQ + 对账兜底）、幻觉治理要四层组合、成本控制要管 TopN 和 token 埋点。只接库不管这些，上线就是答非所问。 |
| ❌ 中文固定 1.5 字一个 token | 没有固定常数。老分词器 cl100k_base 约 0.5~0.7 汉字/token，新分词器（o200k、Qwen、DeepSeek）可到 1~1.8 汉字/token，差好几倍。工程口径是成本测算用目标模型的 tokenizer 实测，入口做 estimateTokens() 预估计入限流额度，不背通用数字。 |
| ❌ 召回 TopN 越多越好 | 恰恰相反。拼进 prompt 的片段越多，token 越贵、噪声越大、模型注意力被稀释，反而更容易答偏。正确做法是召回阶段可以宽（如 Top50），但靠相似度阈值过滤 + Rerank 精排收敛到 Top5 左右再进 prompt，按成本预算定档位。 |
