# Agent、Tool Calling 与 ReAct

> 来源：豆包会话第 3、7、8、9、14 轮，归纳整理。
> 次高频模块。核心记忆锚点：**模型只决策、不执行；执行永远在应用层（Java 侧）**。

## 一、Agent 是什么

Agent（智能体）= **LLM 大脑 + 工具调用 + 记忆 + 规划**，让模型不止「回答问题」，还能「完成任务」。

| 组成 | 对应工程实现 |
| --- | --- |
| 大脑 | LLM 推理（决策调什么工具、怎么组合） |
| 工具 | Tool Calling（见下） |
| 记忆 | Redis 存对话历史 + 摘要压缩（见 ai-05） |
| 规划 | ReAct 循环 / Plan-and-Execute（见下） |

**Agent 与 RAG 的区别（必考）**：RAG 是检索文档知识回答知识类问题，不执行动作；Agent 是 LLM 规划 + 调用外部工具完成任务，侧重任务编排。RAG 可以看作 Agent 的一种工具。

## 二、Tool Calling（工具调用）

### 1. 一句话定义

让大模型在生成回答过程中，主动「点名」要调用某个外部函数/接口/工具，由系统真实执行，再把执行结果交给模型继续推理。**模型本身不执行代码，只负责「决策调什么、参数填什么」**。

### 2. 为什么需要

LLM 两个天然短板：
1. **知识封闭**：不知道实时数据、私有数据
2. **不能执行动作**：只会输出文字，不能查库、发请求、改订单

Tool Calling 让 LLM 从「只会说话」变成「会做事」。

### 3. 核心流程（五步）

1. **定义工具**：把业务能力描述成工具清单（名称、功能描述、参数 JSON Schema）
2. **模型决策**：模型判断需要调工具，输出结构化调用请求（tool_name + 参数 JSON），而不是直接回答
3. **系统执行**：Java 后端解析请求，路由到对应方法/接口，真实执行
4. **结果回传**：执行结果作为 role=tool 消息追加进对话历史
5. **模型作答**：模型基于结果生成最终答案；信息不够可继续调用下一个工具（多步推理）

### 4. Function Calling vs Tool Calling（术语演进）

- **Function Calling**：OpenAI 2023 年最早提出的叫法，专指「让模型输出对函数的调用」
- **Tool Calling**：概念泛化——工具不限于函数，可以是 REST API、数据库查询、代码解释器、文件操作、搜索、另一个 Agent、MCP 服务等
- OpenAI 已在 Chat Completions API 中**废弃 `functions` 参数、统一为 `tools` 参数**；主流框架（LangChain4j、LangGraph）也都叫 Tool
- **面试口径：Function Calling 是 Tool Calling 的特例，Tool Calling 是更通用的现代叫法**

### 5. Tool Calling 提供的价值

1. 突破知识边界（查天气、库存、知识库、数据库）
2. 执行真实动作（下单、改状态、发消息）
3. 多步任务编排（先查订单，再根据订单查物流，模型按每步结果动态规划）
4. 结构化交互（输出符合 Schema 的 JSON，应用层可直接解析，稳定可控）
5. 可审计可插拔（每个工具独立注册、独立鉴权、独立监控）

### 6. 关键点（易考）

- 模型输出的是「调用指令」，执行在应用层
- 一次推理可连续调用多个工具
- **工具 description 写得越清楚，模型选对工具的概率越高**；参数 Schema 要严格
- 必须有最大迭代次数 / 超时保护，防死循环烧 token

## 三、常见 Tool 类型（七大类）

| 类别 | 例子 | 备注 |
| --- | --- | --- |
| 信息检索 | 网页/垂直搜索、RAG 向量检索、SQL 只读查询、天气汇率等第三方 API | 只读，风险低 |
| 业务操作 | 下单、退单、改签、审批触发、发短信/邮件/推送 | **改变系统状态，要鉴权 + 幂等** |
| 代码/计算 | 代码解释器（Python）、预置脚本、精确计算器 | LLM 算不准数，交给代码 |
| 文件文档 | Word/PDF/Excel 读写、格式转换、CSV/JSON 清洗 | 大数据量走脚本不走 LLM |
| 系统运维 | 查日志、查监控、健康检查 | **只读优先，写操作要权限+审计** |
| AI 能力 | 调专用小模型（翻译/摘要/审核/OCR/ASR）、Embedding、文生图 | 模型编排模型 |
| Agent/协作 | 子 Agent 委托、MCP 服务、人机确认环节 | 多智能体架构 |

**面试加分口径**：工具不是越多越好。每个工具都要考虑权限控制、参数校验、异常处理、调用监控、失败降级；**工具描述质量直接决定模型选对工具的概率**。

## 四、代码/脚本工具的使用场景

把「执行一段代码/脚本」包装成 LLM 可调用的 Tool，典型场景：

1. **数据计算与分析**（最高频）：CSV 统计、趋势分析——LLM 做不了精确运算，脚本保证精确可复现
2. **数据处理与转换**：清洗、去重、格式转换；大数据量走脚本比走 LLM 省 token 且准确
3. **报表与可视化**：matplotlib/echarts 生成图表、日报表格
4. **爬虫/数据采集**：注意合规与权限
5. **办公自动化**：批量处理 Word/PDF/Excel
6. **运维辅助**：查日志、统计错误、诊断报告
7. **复杂精确计算**：金融利率税费、统计检验

Java 侧执行脚本的方式（ProcessBuilder）与命令注入防护，见 `ai-05-java-engineering.md` 第五节。

## 五、ReAct 自由循环

### 1. 定义

**ReAct = Re**ason + **Act**（推理 + 行动），出自 2022 年 Yao 等人论文《ReAct: Synergizing Reasoning and Acting in Language Models》。Agent 在循环里交替执行：

```
Thought（思考：我要做什么）
  → Action（行动：调用哪个工具）
    → Observation（观察：工具返回了什么）
      → Thought（根据结果再想下一步）
        → Action → Observation → ...
          → Final Answer（信息够了，输出最终答案）
```

「自由」指：**每步调什么工具、调几次、要不要换工具重试，全由模型自己决定**，直到它认为信息足够才停。

### 2. 价值

1. 多步推理：复杂问题拆步推进
2. 动态规划：按实际返回调整计划，不是预设死流程
3. 容错重试：失败可换参数、换工具
4. 信息充分才作答：减少幻觉

### 3. 最大工程坑：死循环

模型可能反复调用工具不结束（发散、来回横跳、被注入带偏），token 无限烧。**看门狗三件套**：

- **最大迭代轮数**（如 autocava-ai：FINANCE 分支 ≤50 轮、SEARCH 分支有界 FC ≤10 轮）
- **超时控制**：整轮执行超时强杀
- **成本熔断**：token 用量超阈值强制收尾——注意是**强制让模型基于已有信息输出 Final Answer**，而不是直接报错

### 4. 三种循环模式对比（面试可讲）

| 模式 | 特点 | 适用 |
| --- | --- | --- |
| ReAct 自由循环 | 模型自由决定调什么、调几次 | 复杂多步任务，灵活但必须配看门狗 |
| 有界循环（bounded function-call） | 固定最多 N 轮，到轮强制汇总 | 确定性要求高的任务，控成本控风险 |
| Plan-and-Execute | 先出完整计划，再逐步执行 | 任务结构清晰、可预规划 |

## 六、Function Calling 深入（2026-10-14 补充）

> ReAct 的完整实现细节、Agent 范式对比、Agent vs Workflow 见 `ai-07-agent-paradigms.md`。

### 1. 定义

**Function Calling：让大模型在生成回复时，输出一个「对某个函数的调用请求」（函数名 + JSON 参数），由应用程序真正执行，再把结果交回模型继续推理的机制。**

```
用户提问
  → 请求里带上 tools/functions 定义（函数名、描述、参数 JSON Schema）
    → 模型判断需要调用 → 返回 finish_reason=tool_calls + 结构化参数
      → 你的程序执行真实函数
        → 把结果作为 role=tool 消息追加 → 再请求模型
          → 模型基于结果生成自然语言答案
```

### 2. 请求/响应的结构（说得出字段就是细节分）

请求侧传给模型的是**函数的说明书**：

```json
{
  "tools": [{
    "type": "function",
    "function": {
      "name": "get_weather",
      "description": "查询指定城市指定日期的天气",
      "parameters": {
        "type": "object",
        "properties": {
          "city": { "type": "string", "description": "城市名，如北京" },
          "date": { "type": "string", "description": "日期，YYYY-MM-DD" }
        },
        "required": ["city"]
      }
    }
  }]
}
```

模型返回的是**调用意图**（不是结果）：

```json
{
  "finish_reason": "tool_calls",
  "message": {
    "role": "assistant",
    "tool_calls": [{
      "id": "call_abc123",
      "type": "function",
      "function": { "name": "get_weather", "arguments": "{\"city\":\"北京\",\"date\":\"2026-10-15\"}" }
    }]
  }
}
```

你的程序执行后回传：

```json
{ "role": "tool", "tool_call_id": "call_abc123", "content": "北京 10-15 小雨 12~18℃" }
```

### 3. 五个必须答对的点

1. **模型不执行函数**——它只输出结构化调用意图，执行永远在应用层（这是所有相关问题的地基）
2. **描述质量决定选择准确率**——`description` 写清楚「什么时候该用我」，模型才选得对；Schema 越严格，参数幻觉越少
3. **一次可有多个 tool_calls**——支持并行调用；执行完一次性回传多条 tool 消息
4. **由模型决定，不由你决定**——你不能强制它调某个函数，只能通过描述、示例（few-shot）、系统提示提高概率
5. **它只是「机制」，不是「范式」**——Function Calling 提供 Action 能力，ReAct/Plan-and-Execute 才是决定「怎么循环」的推理范式；现代 ReAct 就是用 Function Calling 落地的

### 4. 与其他概念的关系（一张表收口）

| 概念 | 层级 | 关系 |
| --- | --- | --- |
| Function Calling | 接口机制 | Tool Calling 的原始形态（OpenAI 2023 提出，后统一为 `tools` 参数） |
| Tool Calling | 接口机制（泛化） | 工具不限于函数；Function Calling 是其特例 |
| Tool / 工具 | 能力单元 | 被调用的对象（函数、API、脚本、子 Agent、MCP 服务） |
| ReAct / Plan-and-Execute | 推理范式 | 决定「何时、以什么顺序」触发 Function Calling |
| Agent | 系统 | 范式 + 工具 + 记忆 + 执行循环 + 观测的组合体 |

### 5. 常见追问与答法

| 追问 | 答法 |
| --- | --- |
| 模型怎么知道有哪些函数？ | 每次请求随 `tools` 参数把函数说明书（name/description/Schema）传过去，不是把代码给模型 |
| 参数模型编错了怎么办？ | Schema 严格约束 + 应用层参数校验 + 校验失败把错误信息回传，让模型带错误重试 |
| 为什么不能用它替代工作流？ | 调用与否由模型决定，不确定；合规/资金场景必须由代码强控流程 |
| 和 MCP 什么关系？ | MCP 是「工具的标准化接入协议」，解决工具从哪来、如何被发现与鉴权；Function Calling 是「模型怎么发起调用」 |

## 追问链 · 参考答案

| 层级 | 问题 | 参考答案要点 |
| --- | --- | --- |
| L1 | Tool Calling 的完整流程是哪五步？Agent 由哪四要素组成？ | Tool Calling 五步：定义工具（名称+描述+参数 Schema）→ 模型决策输出 tool_calls → Java 后端解析路由真实执行 → 结果以 role=tool 消息回传 → 模型基于结果作答。Agent 四要素：LLM 大脑 + 工具调用 + 记忆（Redis 历史+摘要压缩）+ 规划（ReAct 循环）。核心：模型只决策不执行。 |
| L2 | Function Calling 和 Tool Calling 是什么关系？工具到底是谁执行的？ | Function Calling 是 OpenAI 2023 年最早的叫法，专指输出对函数的调用；Tool Calling 是泛化——工具可以是 REST API、数据库、脚本、MCP 服务等，OpenAI 已把 functions 参数统一为 tools。所以 FC 是 Tool Calling 的特例。执行永远在应用层：模型只输出结构化 JSON 调用意图，Java 侧解析执行。 |
| L3 | 工具调用报错了怎么处理？ | 错误信息不要吞掉也不要直接抛给用户，而是转成一条工具结果消息回传模型——错误也是一种可观察的输入，模型会自己换参数、换工具或换方案重试。应用层配套做参数校验前置、失败计数和最大迭代轮数，防止模型在错误上来回打转烧 token。 |
| L4 | ReAct 死循环怎么防？到轮数上限为什么强制汇总而不是直接报错？ | 看门狗三件套：最大迭代轮数（如自由循环 ≤50 轮、有界 FC ≤10 轮）+ 整轮超时强杀 + token 预算熔断。到上限强制汇总是因为已经花掉的 token 和检索到的信息是沉没价值，让模型基于已有信息输出 Final Answer 还能给用户一个可用结果；直接报错等于整轮白跑，体验和成本双输。 |
| L5 | 什么场景该选有界循环而不是 ReAct 自由循环？ | 三个信号：任务步骤可枚举（如搜车的 CONDITION/LOOKUP/RANKING 固定几步）、成本敏感（自由循环轮数不定、成本不可预估）、结果确定性要求高（合规、资金场景）。有界循环固定上限到轮强制汇总，本质是把任务退化成带自主性的 Workflow；探索型任务才交给 ReAct 配看门狗。 |
| L6 | Function Calling 的 description 写不好会有什么后果？ | description 是模型选工具的唯一依据，写不好会直接误选、漏选工具，而且这个问题很难靠调参或换模型补救——只能改写描述、收紧参数 Schema、减少工具数量。工程上把 description 当接口文档写：说清「什么时候该用我」、给出边界和示例，并控制工具总数。 |

## 误区 · 正解

| ❌ 误区 | ✅ 正解 |
| --- | --- |
| ❌ 大模型调用了我的函数 | 模型从不执行任何函数，它只输出一段结构化 JSON（tool_name + 参数），即「调用意图」。真正的执行在 Java 侧：解析指令、按名路由、反射调用、把结果以 role=tool 消息回传。认清这点才会在应用层做鉴权、参数校验、幂等和审计，而不是指望模型自觉。 |
| ❌ 工具越多 Agent 越强 | 工具增多会稀释模型的选择准确率——description 互相干扰，误选率上升；每个工具还要独立做鉴权、校验、监控、降级，维护成本线性增长。正确做法是按场景收敛工具集，宁少勿多，工具描述写清楚边界；真要扩展能力，用子 Agent 或 MCP 分层而不是全堆在一个上下文里。 |
| ❌ ReAct 循环天然会停 | 不会。模型可能发散、来回横跳、或被注入内容带偏而反复调用不结束，token 无限烧。生产必须配看门狗：最大轮数 + 整轮超时 + token 预算熔断，到上限强制让模型基于已有信息汇总输出，而不是裸跑等它自己想停。 |
