# 写前屏障与写后屏障（Write Barrier）详解

> 主题：写屏障的准确定位、写前 / 写后屏障的实现与用途、与内存屏障的区别、HotSpot 插入点
> 学习日期：2026-10-10
> 关联讲义：`jvm-tricolor-satb-incremental-update.md`（三色标记与漏标解决方案）

## 一、准确定位：写屏障是什么

写屏障（Write Barrier）**不是**锁，**不是** CPU 指令，**不是**内存屏障。它是 **JIT 编译器在「引用（oop）字段赋值」这个动作的两侧插入的一小段代码钩子**，目的是维护 GC 需要的辅助数据结构。

它 hook 的目标非常具体：`obj.field = newValue` 这类 oop 字段的写入（对应字节码 `putfield` / `putstatic` / `aastore`）。

### 一次赋值编译后的实际形态

```
// 应用代码
obj.field = newValue

// JIT 编译后（概念形态）
[写前屏障]                     ← 能读到旧值
store  *field = newValue
[写后屏障]                     ← 知道谁被写入
```

**为什么要有两种位置？** 因为两者需要的信息不同：

- 写前屏障需要**旧值**（被覆盖掉的那个引用），赋值一旦发生旧值就永久丢失 → 必须插在赋值之前
- 写后屏障只需要知道**哪个对象被写入了引用**，不关心旧值 → 可以插在赋值之后

## 二、写前屏障（pre-write barrier）

### 用途：G1 的 SATB

用于记录「将被删除的引用」，服务于三色标记的**原始快照（SATB）**方案 —— 破坏漏标的条件②（灰色对象删除指向白色对象的引用）。

### 伪代码

```java
// 应用线程执行：old.field = newValue
// JIT 在赋值指令【之前】插入：

pre_write_barrier(field) {
    if (field 当前值 != null            // 旧值为空则没有"被删除的引用"
        && 该旧值未被标记                 // 已经黑的不用再记
        && SATB 队列处于活跃状态) {       // 关键：只在并发标记期才活跃
        satb_queue.enqueue(field 当前值);  // 记录被覆盖掉的旧引用
    }
}

*field = newValue;   // 真正的赋值发生在这之后
```

### 三个关键细节

1. **唯一存在理由是「能读到旧值」**：SATB 要的是"快照那一刻还活着"的引用，一旦赋值发生就丢了，所以必须在赋值前拦截。
2. **SATB 队列是 per-thread 的**（HotSpot 的 `SATBMarkQueueSet`）：队列满时溢出（overflow）到全局队列，避免多线程争用全局锁。
3. **快路径设计**：非并发标记期活跃判断为假，屏障退化为一次极廉价的检查。「写屏障很贵」只在**并发标记活跃期**成立。

### 使用者

| 收集器 | 是否使用写前屏障 |
| --- | --- |
| G1 | 是（SATB） |
| Shenandoah | 早期版本用 SATB，后期改为 Brooks Pointer + LRB |
| CMS | **否** |
| Serial / ParNew / Parallel | 否 |
| ZGC | 否（用彩色指针 + 读屏障，是另一条路线） |

## 三、写后屏障（post-write barrier）

### 用途：维护卡表（Card Table）/ RSet

记录「哪个对象的引用被修改了」，把该对象所在的卡标记为脏。服务于：

1. **跨代引用记录**（所有分代收集器）：老年代 → 新生代的引用，让 Minor GC 不必扫全堆
2. **跨 Region 引用记录**（G1）：RSet 的输入
3. **CMS 的增量更新**：破坏漏标条件①

### 伪代码

```java
// 应用线程执行：old.field = newValue
*field = newValue;   // 先赋值

post_write_barrier(field) {
    card = card_table.byte_for(field);  // 定位 field 落在哪张卡
    *card = dirty;                       // 把卡标脏
    if (dirty_card_queue 存在) {
        dirty_card_queue.enqueue(card);  // 异步交给 Refinement 线程
    }
}
// 开启 -XX:+UseCondCardMark 后：先判断这张卡是否已经脏，已脏则跳过
```

### 设计取舍

| 设计点 | 说明 |
| --- | --- |
| 不关心旧值 | 所以可以放在赋值之后 |
| 同一张卡只标脏一次 | 已脏则跳过，避免同一卡上大量写入产生重复队列记录 |
| 卡粒度约 512 字节 | 粒度越细记录越精确但卡表本身占内存越多（时间-空间权衡） |
| `-XX:+UseCondCardMark` | 条件卡标记：先读卡值再决定是否写。减少多线程写同一卡表项的 cache line 伪共享争用，代价是多一次内存读 |
| x86 汇编快路径 | store check 用汇编实现，先比较卡值再决定是否写 |

### 使用者

写后屏障是**分代 GC 的通用基础设施**，几乎所有分代收集器都需要：

| 收集器 | 写后屏障用途 |
| --- | --- |
| Serial / ParNew / Parallel Scavenge | 维护卡表，记录老年代 → 新生代引用 |
| CMS | 维护卡表 + 支撑增量更新 |
| G1 | 维护卡表 → Refinement 线程 → RSet |
| ZGC | 不使用卡表（非分代，无跨代引用概念；JDK21 分代 ZGC 另有设计） |

## 四、写前 / 写后完整对比

| 维度 | 写前屏障 pre-write barrier | 写后屏障 post-write barrier |
| --- | --- | --- |
| 插入位置 | 赋值指令之前 | 赋值指令之后 |
| 能读到的信息 | 旧值（被覆盖的引用） | 新值 + 被写入对象的地址 |
| 核心目的 | 记录「被删除的引用」→ SATB 快照 | 记录「谁被写入了引用」→ 卡表 / RSet |
| 记录载体 | SATB 队列（per-thread） | 卡表 + 脏卡队列 |
| 下游消费者 | 并发标记线程 | Refinement 线程 → RSet |
| 执行频率 | 仅并发标记活跃期 | 每次 oop 字段写入（已脏则跳过） |
| 与漏标的关系 | 破坏条件②（灰删白） | 破坏条件①（黑指白，CMS 增量更新） |
| 使用者 | G1、Shenandoah（早期） | Serial / ParNew / Parallel / CMS / G1 |

**最重要的一条结论**：写后屏障是分代 GC 的通用基础设施（任何分代收集器都需要卡表，否则 Minor GC 只能扫全堆）；写前屏障只有 SATB 系收集器才有。**CMS 没有写前屏障。**

## 五、写屏障 vs 内存屏障（必须分清）

| 维度 | 写屏障 Write Barrier | 内存屏障 Memory Barrier / Fence |
| --- | --- | --- |
| 层次 | GC 层 / JIT 插桩 | JMM + CPU 指令层 |
| 触发点 | oop 字段赋值 | volatile 读写、synchronized 进出、Unsafe |
| 目的 | 维护 GC 辅助数据结构 | 禁止指令重排序、保证可见性与有序性 |
| 分类 | 写前屏障 / 写后屏障 | LoadLoad / StoreStore / LoadStore / StoreLoad |
| 产物 | 卡表 / RSet / SATB 队列 | 无数据结构 |
| 典型实现 | `card_table[..] = dirty` | `mfence`、`lock` 前缀、`sfence` |
| 是否加锁 | 否 | 否（但是 CPU 指令） |

**判定口诀**：问「维护了什么数据结构」→ 写屏障；问「禁止了什么重排」→ 内存屏障。
**唯一交集**：某些 CPU 上 `lock` 前缀同时充当全屏障，这是两者容易被混淆的根源。

## 六、HotSpot 的插入点（加分回答）

屏障不是写死在字节码里的，而是在三个执行引擎中分别插入：

| 执行引擎 | 插入方式 |
| --- | --- |
| 解释器 | 执行 `putfield` / `aastore` 等字节码时调用 runtime stub（慢路径） |
| C1（客户端编译器） | 编译期通过 `BarrierSetC1` 插桩，代码简单 |
| C2（服务端编译器） | 通过 `BarrierSetC2` 插桩，会做内联与快路径优化 |

抽象层次：`BarrierSet` 接口提供 `write_ref_field_pre` / `post_write_barrier`；G1 对应 `G1BarrierSet`，其他分代收集器对应 `CardTableBarrierSet`。

## 七、高频追问链

**主问题：写屏障是内存屏障吗？**
- 追问 1：不是。区别在哪？→ 写屏障是 GC 层钩子维护数据结构；内存屏障是 JMM/CPU 层禁止重排序。
- 追问 2：为什么容易混？→ 某些 CPU 上 `lock` 前缀同时充当全屏障，且两者都插在指令流里。
- 追问 3：判定口诀？→ 问「维护了什么数据结构」是写屏障，问「禁止了什么重排」是内存屏障。

**主问题：写屏障会不会拖慢应用？**
- 落点：会，这是整个应用的税 —— 每次 oop 字段赋值都要过一遍。但有快路径：SATB 写前屏障非标记期直接跳过、卡表写后屏障已脏则跳过、x86 走汇编快路径。
- 追问 1：什么应用受影响最大？→ 写密集、对象引用频繁变更（大量 DTO 转换、树结构频繁改链接）。
- 追问 2：怎么量化？→ 压测对比吞吐；观察 Refinement 线程的 CPU 占用与 RSet 内存占用。

**主问题 G1 为什么需要两种屏障？**
- 落点：两个目标互不替代 —— 写前屏障保证并发标记不漏标（SATB），写后屏障维护 RSet 记录跨 Region 引用。
- 追问 1：CMS 为什么只需要写后屏障？→ CMS 用增量更新，只需记录「新增引用」，不需要旧值。
- 追问 2：G1 能不能只留一种？→ 不能。只留写后屏障就要退回增量更新的重扫模型，停顿不可控；只留写前屏障则 RSet 无法维护，回收时得扫全堆。

**主问题：为什么写前屏障一定要在赋值前？**
- 落点：旧引用一旦被覆盖就丢了，写后执行的屏障拿不到它。SATB 记录的就是「将被删除的引用」。
- 追问：那写后屏障为什么不能在前面？→ 技术上可以（卡表只需知道哪个对象被写入），放在后面更自然：赋值若被优化掉或异常中断，标脏就白做了。

**主问题：`-XX:+UseCondCardMark` 是干什么的？**
- 落点：条件卡标记。默认无条件写脏；开启后先判断卡是否已脏，已脏则跳过。目的是减少多线程写同一张卡导致的 cache line 伪共享争用。
- 追问：代价是什么？→ 多一次内存读，所以是否开启取决于写冲突程度（单线程/低冲突场景反而可能亏）。

## 八、常见误区

| # | 错误说法 | 正确理解 |
| --- | --- | --- |
| 1 | 写屏障就是内存屏障 | 完全不同层次：一个维护 GC 数据结构，一个控制重排序 |
| 2 | 写屏障是一种锁 | 不是锁，是 JIT 插入的代码片段，不加锁、不阻塞 |
| 3 | 写屏障只在 GC 发生时执行 | 每次 oop 字段赋值都要过；非 GC 期走快路径 |
| 4 | G1 只有写前屏障 | 两种都有：写前服务 SATB，写后服务卡表 / RSet |
| 5 | CMS 也有写前屏障 | 没有。CMS 只需要写后屏障 |
| 6 | 写前屏障更贵，所以 G1 比 CMS 慢 | 写前屏障有活跃期判断，非标记期基本零成本；G1 开销主要来自 RSet 内存与 Refinement 线程 |
| 7 | 卡表是 G1 才有的 | 卡表是分代 GC 通用结构，Serial / ParNew / Parallel / CMS 都有 |
| 8 | 写屏障记录是同步处理的 | 只负责入队，由并发标记线程 / Refinement 线程异步消费 |

## 九、一句话总结

**写屏障是 JIT 在 oop 字段赋值两侧插入的钩子：插在前面的能读到旧值，供 SATB 记录「被删除的引用」（G1 用）；插在后面的能知道谁被写入，供卡表记录跨代 / 跨区引用（几乎所有分代收集器都用）。两者都不是锁，也都不是内存屏障。回答时最该强调的一句是：写后屏障是分代 GC 的通用基础设施，写前屏障才是 SATB 系的专属。**
