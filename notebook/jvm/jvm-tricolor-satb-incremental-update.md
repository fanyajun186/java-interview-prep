# 三色标记法、增量更新与 SATB 完整对比

> 主题：三色标记的抽象模型、漏标的两个必要条件、增量更新 vs SATB 的工作流程、以及两者在 CMS / G1 中起作用的阶段
> 学习日期：2026-10-10
> 对应知识地图：`references/01-jvm.md` 第 2.8 节「三色标记法与漏标解决方案」

## 一、三色标记是什么

三色标记不是数据结构，也不是某个收集器的私有技术，而是**并发标记场景下描述对象图遍历状态的一种抽象模型**。它把「遍历整个对象图」这个原本必须一口气做完的工作，拆成可以被中断、可恢复的状态机 —— 这是并发标记能够存在的前提。

| 颜色 | 含义 | 标记结束时的语义 |
| --- | --- | --- |
| 白色 | 还没被 GC 访问到 | 仍是白色 → 判定为垃圾 |
| 灰色 | 自己已被访问，但它引用的对象还没扫描完 | 待处理队列（mark stack）中的对象 |
| 黑色 | 自己已被访问，且它的所有引用也都扫完了 | 存活已确认，本轮不再扫描 |

**状态单向推进：白 → 灰 → 黑。** 关键不变式：**黑色对象不能直接指向白色对象**（强三色不变式）；弱三色不变式允许黑指白，但要求存在一条从灰对象出发、能到达该白对象的路径。

### 为什么需要它

并发标记期间应用线程仍在运行并改写引用。如果只在最后做一次朴素的可达性分析，就会出现「标记时认为死、实际活着」或反之。三色标记把标记过程本身变成可增量推进的，从而让「GC 线程慢慢标、应用线程继续跑」成为可能。

### 严格来说的边界

所有可达性分析（tracing GC）在抽象上都是三色遍历：白 = 未到达、灰 = 待扫描、黑 = 已扫完。但**只有并发标记才需要「三色标记 + 屏障」这一整套机制**来保证不漏标。串行/并行收集器（Serial、ParNew、Parallel Scavenge/Old）全程 STW，应用线程无法改写引用，不存在并发一致性问题。

## 二、漏标（对象消失）的两个必要条件

**两个条件必须同时成立**，白色对象 C 才会被误判为垃圾：

1. **黑色对象 A 新增了一条指向白色对象 C 的引用**（写后屏障可捕获）
2. **灰色对象 B 删除了指向 C 的引用**（写前屏障可捕获），C 因此失去唯一入边

破坏其中任意一个条件，就能解决漏标 —— 这就是增量更新与 SATB 两条技术路线的分岔点。

## 三、增量更新（Incremental Update）工作流程

**核心思路：破坏条件 1 —— 记录「黑色对象新增的引用」。**

| 步骤 | 发生时机 | 具体动作 |
| --- | --- | --- |
| ① | 应用线程执行 `A.field = C` **之后** | 写后屏障触发，把 A 所在的卡标记为脏（dirty card），放入 dirty card queue |
| ② | 并发标记期间 | 并发标记线程消费脏卡，把 A 重新标为灰色，再扫一遍它的引用 |
| ③ | 重新标记（STW） | 以所有被记录的脏对象/脏卡为根重扫 → C 补标为黑色 |

**代价**：重新标记的工作量正比于「并发期间的引用变动量」，与堆大小无关但与写入频率正相关 → **停顿不可预测**。这是 CMS 停顿不可控的直接原因，也是它被 G1 取代的核心动因。

**实现细节**：CMS 用 Mod-Union Table（卡表）记录并发标记期间被修改的引用，重新标记阶段需要重扫根集合（含年轻代指向老年代的引用）+ 处理 Mod-Union Table。

## 四、原始快照（SATB）工作流程

**核心思路：破坏条件 2 —— 记录「被删除的引用」。**

| 步骤 | 发生时机 | 具体动作 |
| --- | --- | --- |
| ① | 应用线程执行 `A.field = C` **之前**（覆盖旧值 oldRef 之前） | 写前屏障拦截，读取被覆盖的旧引用 B → C |
| ② | 并发标记期间 | 旧引用入 SATB 队列，标记线程按「快照时仍然存活」的语义继续遍历它 |
| ③ | 重新标记（STW） | 只需清空剩余队列即结束 → C 因旧引用被记录而保留 |

**代价**：被删引用指向的对象即使后续真的死了，本轮也不回收 → **浮动垃圾（floating garbage）**。换来的收益是重新标记阶段工作量可控且短（只需处理队列积压，不需要重扫整个堆）。

**实现细节**：G1 的 SATB 队列是 per-thread 的（`SATBMarkQueueSet`），队列满时溢出到全局队列；写前屏障有 fast-path，非并发标记期 `is_active()` 为假，屏障基本退化为空操作。

## 五、核心对比

| 维度 | 增量更新 Incremental Update | 原始快照 SATB |
| --- | --- | --- |
| 破坏的漏标条件 | 条件 1：黑新增指向白 | 条件 2：灰删除指向白 |
| 屏障类型 | 写后屏障 post-write barrier | 写前屏障 pre-write barrier |
| 记录内容 | 「谁新增了引用」→ 对象/卡被标脏 | 「哪个引用被删了」→ 记录被覆盖的旧值 |
| 记录载体 | Mod-Union Table + 脏卡队列 | SATB 队列（per-thread，满了溢出全局） |
| 消费者 | 并发标记线程 + 重新标记阶段重扫 | 并发标记线程持续消费 |
| 重新标记做什么 | 以脏对象为根**重扫引用** | **清空剩余队列**即结束 |
| 重新标记耗时 | ∝ 并发期间引用变动量（不可预测） | ∝ 队列积压量（可控且短） |
| 浮动垃圾 | 无 | 有 |
| 策略倾向 | 精确（只补新增） | 保守（宁可多留） |
| 使用者 | CMS | G1、Shenandoah（早期版本） |

**一句话记忆**：增量更新盯「写」，SATB 盯「删」；一个换来精确但要重扫，一个换来可控但要留浮动垃圾。

## 六、哪些回收器用到三色标记

| 收集器 | 需要三色 + 屏障吗 | 并发标记机制 |
| --- | --- | --- |
| Serial / ParNew / Parallel Scavenge / Parallel Old | 不需要 | 全程 STW，应用线程无法改写引用 |
| CMS | 需要 | 增量更新，写后屏障 |
| G1 | 需要 | SATB，写前屏障 |
| Shenandoah | 需要 | 早期用 SATB，后期 Brooks Pointer + LRB |
| ZGC | 需要，实现不同 | 颜色编码进指针（Colored Pointers）+ 读屏障 |

**G1 有两种屏障，CMS 只有一种**：G1 的写前屏障服务 SATB（标记正确性），写后屏障服务卡表（RSet 维护）；CMS 只有写后屏障（既维护卡表又服务增量更新）。

## 七、三色标记在 CMS 与 G1 的起止阶段

| 收集器 | 起点 | 主体 | 终点 |
| --- | --- | --- | --- |
| CMS | 初始标记（STW）：把 GC Roots 直接引用的对象从白转灰，作为种子 | 并发标记：灰出队 → 变黑，其引用对象变灰 | 重新标记（STW）：增量更新补漏标 |
| G1 | 初始标记（STW，搭在 Young GC 上）：确立 SATB 快照起点 | 并发标记：三色遍历 + 消费 SATB 队列 | 重新标记（STW）：处理剩余 SATB 队列 |

两者的阶段名几乎完全相同，所以这个问题真正在考的是：**你能不能说清「起点在初始标记」而不是笼统答「并发标记阶段」。** 严格表述是「初始标记是三色标记的种子阶段，并发标记是它的主体，重新标记是收尾」。

### CMS 阶段与 STW

| 阶段 | STW | 三色标记状态 |
| --- | --- | --- |
| 初始标记 | 是（很快） | 种子阶段，只扫 GC Roots 直接引用 |
| 并发标记 | 否 | 主体，增量推进三色遍历 |
| 重新标记 | 是 | 修正阶段，处理脏卡与新增引用 |
| 并发清除 | 否 | 标记已结束，白色对象被清除 |
| 并发重置 | 否 | 重置内部数据结构 |

### G1 阶段与 STW

| 阶段 | STW | 说明 |
| --- | --- | --- |
| 初始标记 | 是，搭在 Young GC 上 | 确立 SATB 快照起点 |
| 根区域扫描 | 否（并发） | G1 特有，扫描 Survivor Region 中被 RSet 指向的对象 |
| 并发标记 | 否 | 三色遍历主体 + 消费 SATB 队列 |
| 重新标记 | 是 | 处理剩余 SATB 队列 |
| 清理 | 是（很短） | 统计 Region 存活率、回收完全空闲的 Region、选出回收集合 |

## 八、高频追问链

**主问题：既然要 STW 修正，为什么还要并发标记？**
- 追问 1：并发标记的价值是什么？→ 把「遍历整个对象图」这个最大头的工作挪出停顿；STW 的初始标记和重新标记只做「根」和「修正」这类小工作量。
- 追问 2：代价是什么？→ 写屏障的固定开销（每次字段赋值都要过一遍屏障，是整个应用的税）+ 浮动垃圾 / 重扫成本 + 与用户线程抢 CPU。
- 追问 3：什么场景不适合？→ 引用变动极频繁（写密集）时增量更新的重扫量爆炸、Remark 拉长；CMS 更适合读多写少的场景。

**主问题：CMS 的重新标记为什么经常比初始标记长很多？**
- 落点：初始标记只扫 GC Roots 直接引用（数量有限）；重新标记要处理并发期间所有脏卡记录 + 重扫根集合 + 处理年轻代指向老年代的引用（Mod-Union Table）→ 工作量正比于引用变动量。
- 追问 1：怎么缓解？→ 减少对象引用变动；`-XX:CMSScheduleRemarkEdenPenetration` 让 Remark 卡在 Eden 半满时；`-XX:CMSMaxAbortablePrecleanTime` 限制 preclean 时长。
- 追问 2：G1 的 Remark 为什么相对短？→ SATB 队列在并发标记期间被持续消费，尾部清尾量小，且不需要重扫整个堆。

**主问题：SATB 产生的浮动垃圾有什么实际后果？**
- 落点：本轮不回收 → 老年代水位偏高 → 下一轮并发周期更早触发 / 更频繁；分配速率高时可能触发 Concurrent Mode Failure（CMS）或 `to-space exhausted`（G1）→ Full GC。
- 追问 1：怎么缓解？→ 预留空间：CMS 调低 `-XX:CMSInitiatingOccupancyFraction`，G1 调 `-XX:G1ReservePercent` 与 IHOP。
- 追问 2：这是缺陷吗？→ 不是，是 SATB 换来停顿可控的必然代价，属于设计取舍。

**主问题：写前屏障比写后屏障更贵吗？**
- 落点：写前屏障需要在赋值**之前**读一次旧值并判断颜色，多一次读 + 分支判断。
- 追问 1：那 G1 为什么还选它？→ 有快路径优化：非并发标记期 `SATBMarkQueueSet.is_active()` 为假，屏障基本是空操作。
- 追问 2：为什么 CMS 不用写前屏障？→ 它只需要「新增」这个信息，不需要旧值。

**主问题：G1 用 SATB 而不是增量更新，为什么？**
- 落点：Remark 工作量可控且短，符合 G1 的停顿可预测目标；代价是浮动垃圾，而浮动垃圾是「延后回收」而非「正确性错误」，可接受。

## 九、面试问法（附答题骨架）

1. 「讲一下三色标记法。」→ 骨架：三态定义 → 状态单向推进 → 黑不指白的不变式 → 漏标两条件 → 两种屏障解法。
2. 「什么情况下会发生漏标？」→ 骨架：两个条件必须同时成立；缺一个都不会漏。
3. 「写屏障是什么？和内存屏障是一回事吗？」→ 骨架：不是。写屏障是 GC 在字段赋值处插入的钩子（维护卡表 / RSet / SATB），内存屏障是 JMM 与 CPU 层面的指令。
4. 「CMS 用的是什么方案？为什么？」→ 骨架：增量更新 + 写后屏障；精确但 Remark 不可预测 → 是 CMS 停顿不可控的根源。
5. 「G1 为什么改成 SATB？」→ 骨架：破坏条件 2，写前屏障，Remark 只清队列 → 停顿可控；代价是浮动垃圾。
6. 「三色标记在 CMS 和 G1 分别从哪个阶段开始？」→ 骨架：都在初始标记种下灰色集合，主体在并发标记，收尾在重新标记。强调「起点在初始标记」。
7. 「G1 有几种屏障？」→ 骨架：两种。写前服务 SATB，写后服务卡表/RSet。
8. 「浮动垃圾怎么处理？」→ 骨架：等下一轮并发周期回收；用预留空间（G1ReservePercent / CMSInitiatingOccupancyFraction）避免触发 Full GC。
9. 「ZGC 不用写屏障，怎么做并发标记？」→ 骨架：颜色编码进指针（Colored Pointers），读屏障在读取引用时修正颜色；代价是吞吐略降、不支持指针压缩。
10. 「Concurrent Mode Failure 和漏标有关系吗？」→ 骨架：没有直接关系。CMF 是预留空间不足导致的退化，漏标是正确性问题（由屏障保证不发生）。

## 十、常见误区

| # | 错误说法 | 正确理解 |
| --- | --- | --- |
| 1 | 三色标记是 G1 独有的 | 是并发标记的通用抽象，CMS / G1 / Shenandoah / ZGC 都用 |
| 2 | 黑色对象会被重新标成白色 | 标记只单向推进；增量更新是把黑**涂灰**（重扫），不是变白 |
| 3 | SATB 会拷贝一份对象图快照 | 是逻辑快照，不拷贝内存；只把被删除的引用记下来当作快照的一部分 |
| 4 | G1 只有写前屏障 | 写前服务 SATB，写后服务 RSet/卡表，两种都有 |
| 5 | STW 的收集器不需要三色标记 | 抽象上是三色遍历，但没有并发改写，所以不需要屏障机制 |
| 6 | 增量更新和 SATB 的差别只是快慢 | 根本差别是精确 vs 保守，且屏障类型、记录内容、Remark 内容全都不同 |
| 7 | SATB 的 Remark 只是清空队列 | 还要重扫根集合、处理引用链，只是不需要重扫整个老年代 |
| 8 | 三色标记的颜色存在对象头里 | HotSpot 用独立的 marking bitmap；G1 用 prev / next 两张 bitmap 区分「上轮已标记」与「本轮新标记」 |
| 9 | 写屏障就是内存屏障 | 前者是 GC 钩子，后者是 JMM/CPU 层面指令，完全不同的东西 |

## 十一、加分回答（体现深度）

- **HotSpot 的实现**：三色标记的「颜色」并不存在对象头 Mark Word 里，而是用独立的 **marking bitmap**。G1 的并发标记周期使用 prev / next 两张 bitmap，用于区分「上一轮已标记」与「本轮新标记」，这样在重新标记时能正确处理跨周期的情况。
- **SATB 队列的并发设计**：G1 的 `SATBMarkQueueSet` 是 per-thread 队列，避免全局锁竞争；队列满时溢出（overflow）到全局队列，并可能触发标记线程介入。
- **写前屏障的快路径**：非并发标记期 `is_active()` 为假，屏障退化为极廉价的判断，所以「写屏障很贵」在生产上并非绝对 —— 贵的只是标记活跃期。
- **ZGC 的另一条路**：把颜色编码进 64 位指针的高位（Marked0 / Marked1 / Remapped / Finalizable），配合 Load Barrier 实现并发标记与转移，根本不用写屏障。代价是不支持指针压缩（CompressedOops）与吞吐略降。

## 十二、一句话总结

**三色标记把「遍历整个对象图」变成可中断、可恢复的状态机，从而让并发标记成立；代价是必须处理应用线程改写引用带来的漏标问题。漏标的两个条件必须同时成立，于是产生两条路线：CMS 用写后屏障记录「新增」引用、在重新标记里重扫（精确但耗时不可预测），G1 用写前屏障记录「被删」引用、把「快照时活着」当作事实（可控但产生浮动垃圾）。两者的阶段划分几乎一样 —— 初始标记种下灰色集合、并发标记是主体、重新标记收尾 —— 分野全在「用什么机制保证不漏标」。**
