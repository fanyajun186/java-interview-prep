# Redis 主从复制、哨兵与集群：通信与选举

> 面试主线：**主从解决数据冗余，哨兵解决高可用（自动故障转移），Cluster 解决容量与写吞吐的水平扩展**——三者层层递进，先把这个演进逻辑讲清楚，再展开细节。

## 一、主从复制（Replication）

### 1. 拓扑与作用

- 一主多从（也可级联），**写主读从**，实现读写分离与数据热备
- `replicaof <ip> <port>`；主从是**异步复制**——主节点写完立即回客户端，不等从节点确认（这是「主从切换可能丢数据」的根源，也是和 MySQL 半同步的差异点，被追问时必答）

### 2. 全量同步流程（首次上线 / 无法增量时）

```
从节点 --> psync ? -1              （第一次：不知道主节点 replication id）
主节点 --> +FULLRESYNC <replid> <offset>   （回自己的复制 ID 和当前偏移）
主节点 --> bgsave 生成 RDB          （期间新写命令进 replication buffer）
从节点 --> 清空自身数据 → 加载 RDB
主节点 --> 把 buffer 里的增量命令发给从节点
从节点 → 追平 offset，进入命令传播阶段
```

### 3. 增量同步（psync，2.8+）

断线重连后从节点带着自己的 replid + offset 发 `PSYNC`：

- **offset 还在 replication backlog（环形缓冲区，默认 1MB）里** → 主节点只补发缺的增量命令（部分重同步）
- **断得太久、offset 已被覆盖** → 退化全量同步
- 追问点：backlog 大小按「断线时长 × 写入速率」估，`repl-backlog-size` 可调

### 4. 心跳与检测

- 主节点每 10s（repl-ping-replica-period）发 PING；从节点每 1s 上报 `REPLCONF ACK <offset>`（主节点据此检查复制延迟，`min-replicas-to-write` / `min-replicas-max-lag` 可配置「从节点落后太多则拒绝写」，是减少数据丢失的参数）

## 二、哨兵模式（Sentinel）—— 自动故障转移

### 1. 为什么需要哨兵

主从模式里主挂了要**人工切换**，哨兵就是干这件事的自动化进程：监控、通知、自动故障转移、配置提供者（客户端通过哨兵拿当前主节点地址）。

### 2. 架构要求

至少 **3 个哨兵节点（奇数）**，独立部署（不与 Redis 同机）。2 个哨兵不行：挂一个后剩 1 个无法形成 quorum。

### 3. 下线判定（两级，必考）

| 层级 | 谁判定 | 条件 |
| --- | --- | --- |
| **主观下线 SDOWN** | 单个哨兵 | 该哨兵 ping 主节点，超过 `down-after-milliseconds`（默认 30s，常调到秒级）无有效回复 |
| **客观下线 ODOWN** | 哨兵集群 | **≥ `quorum` 个哨兵**（配置文件里设，通常过半）都认为主观下线 → 才启动故障转移 |

设计动机：单哨兵的网络抖动/分区可能误判，多个哨兵投票防脑裂式误切换。

### 4. 哨兵 leader 选举（谁主持故障转移）

ODOWN 后哨兵之间**先选出 leader 主持这次故障转移**，流程是 Raft 风格：
1. 每个发现 ODOWN 的哨兵都可自荐（自增 local epoch，发 `SENTINEL is-master-down-by-addr` 拉票）
2. 每个哨兵**每个 epoch 只能投一票，先到先得**
3. 得到**超过半数（majority，注意不是 quorum）** 票的哨兵成为 leader；一轮没人过半则等待随机时间进入下一轮（quorum 只管判定 ODOWN，leader 选举必须 majority——这是常见混淆点）

### 5. 故障转移流程（leader 哨兵执行）

1. **选新主**：从存活的从节点里挑——排除 `down-after-milliseconds` 内失联的、排除复制积压落后的；按**优先级（replica-priority）→ 复制偏移量最大（数据最全）→ runid 字典序最小**排序取第一
2. 向被选从节点发 `SLAVEOF NO ONE`（升为主）
3. 其余从节点发 `SLAVEOF <新主>` 重新挂载
4. 旧主恢复后（被降级）也被改为跟随新主
5. 哨兵集群更新自身配置 + 通知客户端（发布订阅 `+switch-master` 频道）

### 6. 局限

- **数据容量**：每台都是全量数据，单机内存上限就是集群上限
- **写吞吐**：只有一个主可写，写扩展不了
- 客户端仍需感知哨兵（虽然主流 SDK 已封装）——这两条局限正是引出 Cluster 的过渡话术

## 三、Cluster 集群 —— 分片 + 高可用一体

### 1. 核心设计

- **16384 个哈希槽**：`slot = CRC16(key) % 16384`，槽按区间分配给各主节点
- 数据按 key 分片到不同主节点，**每个主节点只存一部分数据**——容量和写吞吐都水平扩展了
- 官方建议至少 **6 节点（3 主 3 从）**；哨兵不再需要：主从 + 选举内置在集群协议里

### 2. 为什么是 16384 个槽（高频追问）

- 心跳包里要带本节点负责的槽位图：16384 位 = 2KB，**65336（哈希空间全量）要 8KB**，gossip 心跳太重
- Redis Cluster 上限建议 1000 主节点，16384 个槽足够分配
- 槽是「压缩后的哈希空间」：客户端和服务端都只需维护「槽 → 节点」的映射，节点数少时（如 3 主）槽数远小于节点数会限制分片粒度

### 3. 节点间通信：Gossip 协议

- 每个节点与部分节点维持 TCP 长连接，**周期性（每秒）交换 PING/PONG**，消息里带：自身槽位表、认知的节点状态等
- 消息类型：`MEET`（加入集群握手）、`PING/PONG`（心跳+状态交换）、`FAIL`（广播某节点客观下线）、`PUBLISH`（发布订阅传播）
- 收到 PING 的节点随机选部分节点转播（gossip 的「传八卦」），最终一致收敛
- 新节点加入：对任意节点发 `CLUSTER MEET` → 通过 gossip 扩散

### 4. 下线判定与选举（和哨兵同构但内置）

| 层级 | 机制 |
| --- | --- |
| 疑似下线 PFAIL | 单节点 gossip 中发现某主节点超过 `cluster-node-timeout`（默认 15s）不可达 → 本地标记 PFAIL（疑似） |
| 确认下线 FAIL | **超过半数主节点**都报告某主 PFAIL → 第一个发现的节点广播 `FAIL`，全集群公认 |
| 从节点竞选 | FAIL 主节点的从节点发起选举（Raft 风格）：自增 epoch 拉票 → **获得超过半数主节点投票**的从节点当选新主 |
| 新主上位 | 执行 `SLAVEOF NO ONE` 等价逻辑，广播 PONG 携带新槽位配置，接管槽 |

从节点投票时**偏投复制偏移量最大的**（数据最全）——和哨兵选新主的排序逻辑一致。**半数以上主节点挂掉或某槽全覆盖不可用时，整个集群默认不可写**（`cluster-require-full-coverage yes` 可放开）。

### 5. 客户端怎么找数据：MOVED / ASK 重定向

- 客户端（Smart Client）本地缓存「槽 → 节点」映射，直接打对节点（大多数请求）
- 打错节点时服务端回 **`MOVED`**：槽已归别的节点管（永久性）→ 客户端更新本地映射
- **`ASK`**：槽正在迁移中的临时重定向（客户端带 ASKING 去目标节点试这一次，**不更新**本地映射）——MOVED/ASK 的区别是经典追问
- **hash tag**：`{user1000}.profile`、`{user1000}.orders` 花括号内的内容才算哈希 → 强制同槽，支持多 key 操作和事务

### 6. 在线槽迁移（扩容 / 缩容，追问热点）

**全程不停写。** 顺序是**先标记目标节点，再标记源节点**：

1. 目标节点：`CLUSTER SETSLOT <slot> IMPORTING <source-id>`
2. 源节点：`CLUSTER SETSLOT <slot> MIGRATING <target-id>`
3. 源节点逐个 key 发 `MIGRATE` 搬到目标节点（**迁移粒度是单个 key，不是槽**，所以同一个 key 在任意时刻只存在于一边）
4. 迁完后：`CLUSTER SETSLOT <slot> NODE <target-id>`，槽所有权正式易主

迁移期间请求的三条分支：

| key 状态 | 源节点行为 |
| --- | --- |
| key 还在源节点 | 正常执行，客户端无感 |
| key 已搬到目标 | 回 `-ASK <slot> <target>`，客户端带 `ASKING` 去目标节点取这一次 |
| 槽已迁完 | 回 `-MOVED`，永久重定向 |

> <span style="color:red">多 key 命令（`MGET` / 事务 / Lua）只要有一个 key 不在本地，直接返回 `-TRYAGAIN`</span>，客户端需稍后重试——这是迁移期间最容易踩的坑。
> 另外：目标节点此时**不算持有该槽**，不带 `ASKING` 直接访问会被拒绝并回 MOVED，请求会来回弹。
> 代价：`MIGRATE` 大 key 会阻塞源节点，**迁移必须挑低峰**。

### 7. 集群模式下的两处认知校正

- **从节点默认不可写**：只读（可用 `READONLY` 开启读，但始终不允许写）；
- <span style="color:red">`min-replicas-to-write` 在集群模式下的防护不可靠</span>：从节点进程集体挂掉（不是网络分区）也会让主节点拒写，造成假故障不可用。Cluster 挡脑裂真正靠的是**过半主节点投票**（少数派选不出第二个主）加 `cluster-require-full-coverage yes`（少数派槽不全 → 直接 CLUSTERDOWN 停写），改 `no` 才是真正的脑裂窗口。详细推演见 `redis-07-cluster-deep-dive.md` 第八节。

## 四、三种模式对比总表

| 维度 | 主从 | 哨兵 | Cluster |
| --- | --- | --- | --- |
| 数据分布 | 每台全量 | 每台全量 | 按 16384 槽分片 |
| 写扩展 | ✗（单主写） | ✗ | ✓ |
| 容量扩展 | ✗ | ✗ | ✓ |
| 高可用 | 人工切换 | 哨兵自动切换 | 内置选举自动切换 |
| 故障判定者 | - | 独立哨兵进程（quorum） | 集群主节点本身（半数） |
| 客户端复杂度 | 低 | 中（找哨兵问主） | 中（Smart Client 缓存槽映射 + 重定向处理） |

## 追问链 · 参考答案

| 层级 | 问题 | 参考答案要点 |
| --- | --- | --- |
| L1 | 主从复制、哨兵、Cluster 分别解决什么问题？为什么要层层演进？ | 主从解决数据冗余与读写分离（写主读从、异步复制）；哨兵解决高可用，自动完成 SDOWN/ODOWN 判定与故障转移；Cluster 解决容量与写吞吐的水平扩展（16384 槽分片 + 内置选举）。演进逻辑是：先有冗余，再补自动切换，最后才解决单主写与单机容量的天花板。 |
| L2 | 主观下线和客观下线的区别？哨兵选 leader 要几票？ | SDOWN 是单个哨兵 ping 主节点超过 `down-after-milliseconds`（默认 30s，常调到秒级）无有效回复的本地判定；ODOWN 是 ≥ `quorum` 个哨兵都报 SDOWN 才成立。leader 选举必须拿到 **majority**（过半数哨兵票，先到先得、每 epoch 一票），与 quorum 无关——这是最常被混淆的点。 |
| L3 | psync 增量同步靠什么？backlog 太小会怎样？ | 靠主节点的 replication backlog（环形缓冲区，默认 1MB）加 replid + offset：从节点重连带自己的 offset 发 `PSYNC`，offset 还在 backlog 里就只补发缺失的增量；被覆盖则退化为全量 `bgsave` + RDB。backlog 按「断线时长 × 写入速率」估算，用 `repl-backlog-size` 调大以避免频繁全量同步。 |
| L4 | MOVED 和 ASK 的区别？槽迁移期间请求怎么走？ | `MOVED` 表示槽已永久归属别的节点，客户端要更新本地槽映射后重发；`ASK` 是迁移中的临时重定向，客户端带 `ASKING` 去目标节点试这一次，**不更新**映射。迁移期间先打源节点，key 已迁走则回 ASK 指向目标，目标尚未收到则返回 `TRYAGAIN` 让客户端稍后重试。 |
| L5 | 为什么是 16384 个槽？Cluster 选举和哨兵选举机制上有什么异同？ | 心跳包要带槽位图，16384 位 = 2KB，而 CRC16 全空间 65536 要 8KB，gossip 太重；官方建议上限 1000 主节点，16384 槽足够分配。选举同为 Raft 风格、都要求过半，但主体不同：哨兵是哨兵投哨兵选 leader 主持切换，Cluster 是主节点投票给从节点选新主。 |
| L6 | 主从是异步复制，failover 时已回客户端但没同步的数据怎么办？ | 找不回来：主节点写完立即回 ack，不等从节点确认，这部分数据随主节点宕机丢失。缓解手段是 `min-replicas-to-write` / `min-replicas-max-lag`，让从节点落后过多时主节点拒绝写；但对强一致诉求，正确认知是别把 Redis 当主存储，资金类数据应以数据库为准、Redis 只做加速。 |
| L7 | 槽迁移期间集群能正常处理请求吗？多 key 命令怎么办？ | 能，全程在线不停写。顺序是先给目标节点标 `IMPORTING`，再给源节点标 `MIGRATING`，然后逐 key `MIGRATE`。key 还在源节点就正常执行；已搬走则回 `ASK` 让客户端带 `ASKING` 去目标取这一次；全部迁完后用 `CLUSTER SETSLOT ... NODE` 切所有权，此后回 `MOVED`。多 key 命令只要有一个 key 不在本地，返回 `-TRYAGAIN` 让客户端稍后重试。迁移大 key 会阻塞源节点，须挑低峰。 |
| L8 | 客户端请求打到一个已经宕掉的节点，MOVED 从哪来？ | 宕掉的进程回不了任何 RESP 响应，客户端拿到的是连接超时 / IOException。客户端捕获异常后随机改问集群里其他存活节点，**由那个存活节点校验槽归属后回 MOVED**。若此时故障转移还没完成、该槽无主，存活节点回的是 `-CLUSTERDOWN The cluster is down`，不会是 MOVED。 |

## 误区 · 正解

| ❌ 误区 | ✅ 正解 |
| --- | --- |
| 「哨兵数量就等于 quorum」 | quorum 是配置文件里判定 ODOWN 的票数门槛，leader 选举另需 **majority**（超过半数哨兵投票，每 epoch 一票、先到先得）。例如 3 个哨兵配 quorum 2：2 个认为下线即判 ODOWN，但 leader 仍要拿到 ≥ 2 票。工程上哨兵取奇数、quorum 取过半，两者不可混为一谈。 |
| 「Cluster 里从节点也能写」 | 从节点只做副本，默认不可写（只可用 `READONLY` 开启读）；多主也不等于任意主都能写任意 key——key 按 `CRC16(key) % 16384` 归属固定主节点，写错节点会被 `MOVED` 重定向。需要多 key 操作或事务时，用 hash tag（`{user1000}.profile`）强制落同槽。 |
| 「gossip 有 FAIL 广播就不用再判定下线了」 | FAIL 广播的前提本来就是**超过半数主节点**已报告 PFAIL，广播只是把这个结论扩散给全集群（含从节点），并非替代判定。完整链路是：单节点超过 `cluster-node-timeout`（默认 15s）不可达 → 本地标 PFAIL → 半数主节点确认 → 由第一个发现的节点广播 FAIL。 |
| 「主从复制是同步的」 | 是异步复制：主节点写完立即回客户端，不等从节点确认，这是故障切换丢数据的根源。工程上用 `min-replicas-to-write` + `min-replicas-max-lag` 在从节点落后过多时拒绝写，用 `INFO replication` 里主从 `repl_offset` 的差值监控延迟；强一致诉求不要把 Redis 当主存储。 |
| 「Redis Cluster 靠 `min-replicas-to-write` 防脑裂」 | 该参数在集群模式下<span style="color:red">生效但不可靠</span>——从节点进程集体挂掉（并非网络分区）也会让主节点拒写，造成假故障不可用，很多团队因此不开。Cluster 挡脑裂真正靠的是**过半主节点投票**（少数派拿不到多数票，选不出第二个主）加 `cluster-require-full-coverage yes`（少数派槽覆盖不全 → 直接 CLUSTERDOWN 停写）；把它改成 `no` 才是真正的脑裂窗口。 |
