# Redis 缓存与数据库一致性：先删缓存还是先改库

> 这题表面在问「缓存和库谁先动」，实际在考**你能不能把四种顺序组合的并发竞态走清楚，并记住 Cache Aside 为什么是业界默认**。  
> 一句话主线：**读走缓存、写走库、写完删缓存（Cache Aside）+ 删除失败重试 + 过期兜底**，覆盖绝大多数业务场景；残留脏窗口用延迟双删再压一压，真要强一致只能串行化。

---

## 一、四种顺序组合，坑逐个走一遍

更新一条数据时，缓存和数据库谁先动？四种组合各有各的雷。

### 方案一：先更新缓存，再更新库

库更新失败，缓存里就是个错误值，得等到过期才恢复。**直接排除。**

### 方案二：先更新库，再更新缓存

看起来合理，但并发下会错乱：

```
线程 A：更新库 stock=10
线程 B：更新库 stock=8
线程 B：更新缓存 stock=8
线程 A：更新缓存 stock=10   ← 库里是 8，缓存是 10，脏了
```

两个线程改库的顺序和改缓存的顺序不一致，缓存就停在旧值上。而且「更新缓存」本身不划算——数据之后很久没人读，这次写就是白干。

### 方案三：先删缓存，再更新库

删掉缓存，下次读自然从库加载新值。但有窗口：

```
线程 A：删缓存
线程 B：读缓存 miss → 读库（还是旧值 10）→ 写回缓存 10
线程 A：更新库为 8
```

结果缓存里是旧值 10，直到下次过期。读比写快时这个窗口很容易撞上（读线程在写线程改完库之前就把旧值读回并写进了缓存）。

### 方案四：先更新库，再删缓存（推荐）

业界通行的 **Cache Aside Pattern**：

```java
db.update(data);
redis.del("key");      // 删掉，让下次读重新加载
```

**为什么最稳？** 删除是最后一步且极快。要出现脏数据，必须同时满足：**缓存刚好为空（刚过期或被前一次删除清空）+ 一个读线程在写库前读到旧值 + 写回缓存又恰好落在删缓存之后**——也就是说，这&#x4E2A;**<u>读</u>未命中回源（查库 + 写缓存）**&#x5FC5;须&#x6BD4;**<u>写</u>操作（改库 + 删缓存）更慢**，从而把旧值「横跨」过整个写操作写回去。这一特定时序窗口本身就极窄，再加上缓存得恰好为空，所以实际概率极低。

> ⚠️ 常见误写：「概率极低（读要比写快，且写回要在删之后）」是自相矛盾且方向反了的——读比写快时写回发生在删除之前、随后被清掉，反而不会脏；真正会脏的是「读比写慢、把旧值横跨过写操作写回」。

**为什么是「删」不是「更新」缓存：** 一是避免并发写乱序（方案二那种坑），二是懒加载——被读了才重建，避免冷数据无效写入。

## 二、删失败了怎么办（方案四的软肋，三个兜底）

**重试**：**删除失败的请求丢进消息队列，异步重试到成功**。

**订阅 binlog**：用 Canal 监听 MySQL binlog，数据一变自动删对应缓存，业务代码完全不用关心删除，拆得最开，也是大厂主流做法。

**过期时间兜底**：所有缓存 key 都设过期，即使删除失败最坏也能过期自愈。这条无脑加上。

## 三、残留脏窗口怎么补（延迟双删与串行化）

**上面两节都是最终一致**：Cache Aside **靠窄窗口加过期时间兜底**，删除失败靠重试和订阅 binlog 补。延迟双删属于同一层的补偿手段，只是把残留窗口再压一压，**它不提供强一致**：等待期间缓存仍可能是旧值，第二次删一样会失败，期间若插入新写还会出现更复杂的交错。真正称得上强一致的只有本节末尾的串行化。

延迟双删有两种形态，判据只有一条：第一次删发生在改库之前还是之后。两种写法在资料里都叫这个名字，但骨架和要补的窗口完全不同，混着讲最容易被追问翻车。

**经典形态：先删缓存，改库，延迟后再删**，骨架是方案三。

```java
redis.del(key);          // 第一次删，清空战场
db.update(data);         // 改库
// 等待并发读把旧值写完（生产用延迟队列，不在请求线程里 sleep）
redis.del(key);          // 第二次删，清掉期间被写回的旧值
```

它专门补方案三那个窗口：A 删缓存之后、改库之前，B 读 miss 拿到库里旧值并写回缓存，A 改完库后缓存长期停在旧值。第一次删让 B 一定回源，等待让 B 把脏值写完，第二次删把 B 刚写进去的脏值清掉，三步缺一不可，所以「先删」不能挪到改库之后。

**变体形态：先改库，删，延迟后再删**，骨架是方案四 Cache Aside。

```java
db.update(data);
redis.del(key);          // 常规失效缓存
// 延迟后再删一次
redis.del(key);          // 清掉第一次删之后才写回的旧值
```

它补的不是方案三的窗口，而是第一次删之后才写回的旧值，主要来源是读未命中回源比写操作更慢、把旧值横跨过删除动作写回（方案四的极窄窗口），以及读写分离下从库还没同步完就被回源读到。第一次删只是常规失效缓存，第二次删才是补偿，所以判据始终是「第一次删在改库之前还是之后」。

| 对比项     | 经典延迟双删                       | 变体（先改库后两次删）                    |
| ------- | ---------------------------- | ------------------------------ |
| 时序      | `del → db.update → 延迟 → del` | `db.update → del → 延迟 → del`   |
| 骨架      | 方案三，先删后改库                    | 方案四，Cache Aside                |
| 第一次删的作用 | 清空战场，让后续读请求全部回源              | 常规失效缓存                         |
| 第二次删清什么 | 删缓存后、改库前被并发读写回的旧值            | 第一次删之后才写回的旧值，来源是慢读横跨写操作或主从同步延迟 |
| 延迟时长依据  | 读库加写回缓存的耗时                   | 主从延迟 P99 加回源耗时                 |

延迟时长不是拍脑袋的 500ms。经典形态要大于「读库旧值加写回缓存」的耗时，变体在读写分离下还要叠加主从同步延迟，工程上取监控里的 P99 而不是平均值。短了慢读会在第二次删之后才写回旧值，等于白删；长了把旧值暴露窗口主动拉长。

生产落地有三个必须注意的点。一是 `Thread.sleep` 占住请求线程，拖慢接口还降低吞吐，进程重启或扩容时内存里的延迟任务直接丢失，第二次删就没了，应该改用持久化的延迟消息队列、定时任务表，或者订阅 binlog 后延迟消费，这也正是第二节 MQ 重试与第四节 Canal 能顺带解决的事。二是第二次删同样可能失败，所以删除失败重试和过期时间兜底一条都不能省，延迟双删不能替代它们。三是它只适合历史系统改造、TTL 偏长且允许短暂旧读的场景，余额、库存、权限撤销这类决策不要靠概率兜。

**串行化**：同一 key 的读写路由到同一队列串行处理，或用分布式锁把读写串行起来，一致性有了性能掉一截，一般只在资金类用。它是这一节里唯一能称得上强一致的方案。

---

## 四、更省心的组合：Canal 订阅 binlog

Canal 伪装成 MySQL 从库，拉取 binlog 解析成行变更事件，业务侧监听后删缓存。这样一来，连「删除失败的重试」也顺带解决，业务代码里完全不用写删缓存的逻辑。

---

## 五、两个容易忽略的细节

**回源并发重复写**：读请求没命中时回源，先查库再写缓存，这一步多个线程可能并发重复写同一值，但写的是相同内容，无害，不必为了它加锁。  
（注意：这里「无害」指的是**数据正确性**无害；高并发下它属&#x4E8E;**<u>缓存击穿/狗群效应的</u>** DB 压力问题，可用互斥（singleflight）或互斥重建来缓解，而非防错。）

**库存这类强敏感数据**：干脆不走缓存写，只让缓存承担读，写完全由库扛，缓存超时短一点（比如 1 秒），脏数据窗口自然就小。代价是缓存命中率下降、回源压力上升，适合读多写极少且能接受短延迟的场景。

---

## 六、选型看业务容忍度

- 商品标题、描述这类：几秒不一致无所谓，**Cache Aside 足够**；
- 余额、库存这类：宁可降级慢一点也要先后一致，那就上**串行化或分布式锁**。

一句话：**读走缓存、写走库、写完删缓存（Cache Aside）+ 删除失败重试 + 过期兜底**，这套组合覆盖绝大多数业务场景。

## 勘误说明（相对原文来源文章的修正）

- 原文方案四把脏数据概率低的原因写成「读要比写快，且写回要在删之后」，该句自相矛盾且方向反了，已修正为「读未命中回源比写操作更慢、把旧值横跨过写操作写回」这一准确条件。
- 原文第三节把延迟双删写成「更新库后 sleep 再删一次，清掉方案三那种读回旧值的脏数据」，代码用的是方案四骨架、说明却指向方案三的窗口，骨架与目标对不上；已按两种形态拆开，并把它从「强一致」降级为提高最终一致概率的补偿手段，详见第三节。
- 其余内容（四种方案、Canal、过期兜底、串行化、回源并发、库存设计）经复核均为标准且准确的表述，原文照收。

## 误区 · 正解

| ❌ 误区              | ✅ 正解                                                                                    |
| ----------------- | --------------------------------------------------------------------------------------- |
| 「先更新缓存再更新库」可以接受   | 库更新失败就留下错误值，且要等过期才恢复，**直接排除**；正确做法是 Cache Aside（改库后删缓存）。                                |
| 方案四（先改库再删缓存）绝对不会脏 | 极低概率窗口仍存在：读未命中回源比写操作更慢、且把旧值横跨过写操作在删除之后写回。延迟双删只压低概率，强一致得靠串行化。见第三节。                       |
| 删缓存失败无所谓          | 删除失败 = 缓存留旧值，会脏。必须兜底：MQ 重试 / Canal 订阅 binlog / 过期时间兜底（这条无条件加上）。                         |
| 回源并发重复写缓存要加锁防脏    | 写的是相同内容，**数据正确性无害**；它是缓存击穿/狗群的 DB 压力问题，用互斥重建（singleflight）缓解，不是防错。                      |
| 延迟双删的 sleep 随便设   | 时长要覆盖读库加写回缓存的 P99，读写分离还要叠加主从延迟；`Thread.sleep` 占请求线程且重启丢任务，生产改用延迟消息队列或 binlog 延迟消费。见第三节。 |

## 追问链 · 参考答案

| 层级 | 问题                              | 参考答案要点                                                                                                                                                         |
| -- | ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| L1 | 先更新缓存再更新库为什么不行？                 | 库更新失败时缓存已写入新值，留下错误数据且只能等过期恢复，所以直接排除。                                                                                                                           |
| L2 | 先更新库再更新缓存，并发下为什么会脏？             | 两个线程改库和改缓存的顺序会错乱：A 先改库、B 后改库并先写缓存、A 再写缓存，结果库是 B 的值、缓存是 A 的旧值。且「更新缓存」对冷数据是无用写入。                                                                                 |
| L3 | 先删缓存再更新库的问题窗口是什么？               | A 删缓存后，B 读 miss 读到旧值并写回缓存，A 才更新库——缓存留下旧值直到过期。读比写快时这个窗口容易撞上。                                                                                                    |
| L4 | 为什么业界选「先更新库，再删缓存」（Cache Aside）？ | 删除是最后一步且极快；脏数据需要「缓存刚好为空 + 读在写库前读到旧值 + 写回横跨在删除之后」这一极窄时序才出现。且「删」而非「更新」能避免并发写乱序、实现懒加载。                                                                            |
| L5 | 删缓存失败了怎么兜底？                     | 三选：① 失败请求进 MQ 异步重试；② Canal 订阅 binlog 自动删；③ 所有 key 设过期时间，最坏过期自愈（无条件加）。                                                                                          |
| L6 | 延迟双删有哪两种形态？各自补什么窗口？             | 经典形态是 `del → 改库 → 延迟 → del`，骨架为方案三，第二次删清掉删缓存到改库之间被并发读写回的旧值；变体是 `改库 → del → 延迟 → del`，骨架为方案四，清的是慢读横跨写操作或主从延迟造成的旧值回填。两者都只是最终一致，第二次删也会失败；强一致靠同 key 串行化或分布式锁。见第三节。 |
| L7 | Canal 怎么解决缓存删除？                 | Canal 伪装成 MySQL 从库拉 binlog，解析成行变更事件，业务侧监听后删缓存；删除失败的重试也一并解决，业务代码零删缓存逻辑。                                                                                         |
| L8 | 读未命中时多线程并发回源写缓存，要不要加锁？          | 写的是相同内容，正确性无害，不必为防错加锁；但高并发是缓存击穿的 DB 压力问题，可用互斥重建（singleflight）缓解。                                                                                               |
