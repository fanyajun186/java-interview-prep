# 场景题：设计一个秒杀系统

> 秒杀是考察「高并发 + 一致性 + 兜底」最经典的场景。和红包题共享同一条主链路：**库存前置到 Redis → 原子预扣 → MQ 异步落库 → 对账兜底**，但追问点更集中在**限流削峰、防刷、热点 key**。
> 建议与 `scenario-01-red-packet.md` 对照看，两题答案高度复用。

## 一、先澄清

| 维度 | 要问清什么 |
| --- | --- |
| 规模 | 峰值 QPS、参与人数、单个商品库存量（通常是「少量库存 + 海量请求」） |
| 规则 | 一人几单？是否需要下单后付款？未付款多久释放库存？ |
| 一致性 | 能否超卖？（**不能**，这是资金/履约问题）能否少卖？（可以，但要对账） |
| 业务 | 是否需要预约、风控、验证码、答题？ |

**默认口径**：单 SKU 库存 100，峰值十万级 QPS，一人一单，下单后 5 分钟未支付自动释放。

## 二、整体架构

```text
用户 → CDN/静态页 → 网关（限流 / 风控 / 签名校验） → 秒杀服务 → Redis（库存、一人一单）
                                                        ↓ 预扣成功
                                                      MQ（削峰）
                                                        ↓
                                                  订单服务 → MySQL（订单 / 库存 / 流水）
```

三条设计主线：
1. **把库存决策前移到 Redis**，DB 不参与瞬时竞争；
2. **用 MQ 削峰**，把「瞬时 10 万 QPS」变成「DB 能承受的匀速消费」；
3. **层层拦截**，让 99% 的请求在到达核心逻辑前就被挡掉。

## 三、库存预热

活动开始前，把 DB 里的可售库存同步到 Redis：

```text
SET seckill:stock:{skuId} 100
SADD seckill:sku:all {skuId}
```

**为什么必须预热**：秒杀开始的瞬间如果去 DB 查库存，连接数和行锁会立刻被打爆；预热后「查库存 + 扣库存」全在内存里完成。

**一致性要点**：
- 预热任务要幂等，重复执行不覆盖已扣减的值（用 `SETNX` 或直接由运营后台一次性触发）；
- DB 库存是权威源，Redis 库存是「加速副本」；活动结束后以 DB 为准对账。

## 四、Redis 预扣：必须用 Lua

**错误做法**：先 `GET` 判断再 `DECR`。两步之间不是原子的，并发下会超卖。

**正确做法**：把判断和扣减写进一个 Lua 脚本，Redis 单线程执行，天然原子：

```lua
-- KEYS[1]: 库存 key   返回: 1=扣减成功  0=库存不足
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil or stock <= 0 then
    return 0
end
redis.call('DECR', KEYS[1])
return 1
```

```java
// Spring Data Redis 调用
private static final DefaultRedisScript<Long> DEDUCT_SCRIPT = new DefaultRedisScript<>();
static {
    DEDUCT_SCRIPT.setScriptText("local stock = tonumber(redis.call('GET', KEYS[1])) " +
        "if stock == nil or stock <= 0 then return 0 end " +
        "redis.call('DECR', KEYS[1]) return 1");
    DEDUCT_SCRIPT.setResultType(Long.class);
}

public boolean tryDeduct(Long skuId) {
    Long r = redisTemplate.execute(DEDUCT_SCRIPT, List.of("seckill:stock:" + skuId));
    return Long.valueOf(1).equals(r);
}
```

**为什么不用分布式锁**：`DECR` 本身原子，Lua 保证复合操作原子。加锁只是把并行变串行，白白牺牲吞吐——这是本题最常见的扣分点。

## 五、一人一单与防刷

| 手段 | 实现 | 作用 |
| --- | --- | --- |
| **一人一单** | `SETNX seckill:order:{skuId}:{userId} 1`，或 DB 唯一索引 `(sku_id, user_id)` | 防止同一用户重复下单 |
| 接口隐藏 | 活动开始才下发秒杀路径/token | 防止脚本提前刷接口 |
| 网关限流 | 令牌桶 / 漏桶，按 IP + 用户维度 | 削掉绝大部分无效流量 |
| 答题 / 验证码 | 下单前弹题 | 拉长请求时间，削峰 |
| 风控名单 | 历史刷单用户直接拒绝 | 精准拦截 |
| 库存分桶 | 100 库存拆 10 个 key 各 10 个，随机路由 | 降低单 key 竞争，兼具防刷 |

**兜底**：DB 唯一索引是最后一道防线，Redis 的去重可能失效（宕机、过期），最终一致性靠 DB 约束保证。

## 六、MQ 异步下单

```text
预扣成功 → 返回「排队中」→ 发 MQ（可靠投递）→ 订单服务消费
   └ 消费：DB 行级 CAS 扣库存 → 创建订单 → 写流水 → 更新 Redis 状态为「已确认」
```

**为什么同步走 DB 不行**：秒杀的瞬时 QPS 远超 DB 的行锁吞吐，会在库存行上排队甚至死锁超时。MQ 把并发削峰成可控速率。

**失败兜底**：
- 消费失败 → MQ 重试 + 死信队列 + 告警；
- 下单最终失败 → **回补 Redis 库存**（`INCR`），避免少卖；
- 订单超时未支付 → 同样回补 Redis 与 DB；
- 日终对账：`DB 初始库存 = DB 已售 + DB 剩余`，且 `Redis 剩余 = DB 剩余`。

## 七、限流削峰（分层拦截）

```text
第 1 层：CDN / 静态资源       —— 按钮置灰、页面静态化，别让用户白点
第 2 层：网关限流              —— 令牌桶，超量直接返回「活动太火爆」
第 3 层：用户维度限流          —— Redis 计数器，单用户 1 秒 1 次
第 4 层：业务校验              —— 活动时间、库存、一人一单
第 5 层：DB 行级 CAS           —— 最后一道，保证不超卖
```

**削峰的两种思路**：
- **拦**：限流直接拒绝（用户体验差但实现简单）；
- **缓**：答题/验证码/排队页，把请求拉平到一段时间内（体验好，需要额外交互）。

## 八、热点 key 问题

单个 SKU 的库存 key 是天然热点，所有请求打同一个 key、同一个 Redis 实例。

| 方案 | 说明 |
| --- | --- |
| **库存分桶** | 把 100 拆成 `stock:{sku}:0..9` 各 10 个，请求随机/哈希路由到某个桶；桶空了换下一个 |
| 多副本 | 同一 key 复制 N 份分布在不同实例（读扩展，写仍需聚合） |
| 本地缓存 | 库存为 0 后本地标记「已售罄」，直接返回，不再打 Redis |

**分桶的代价**：可能出现「某桶有货但用户没路由到」导致少卖；缓解办法是桶空后重试其他桶，或活动末期合并桶。

## 九、面试答题模板

**60 秒版本**：

> 我先确认两点：库存量和是否限制一人一单。核心矛盾是**瞬时高并发 vs 不能超卖**。
> 我的方案是四层：第一，活动前把库存预热到 Redis，让库存判断和扣减都在内存完成；第二，用 Lua 脚本保证「判断 + 扣减」原子性，这是不超卖的关键；第三，预扣成功后立刻返回「排队中」，通过 MQ 异步创建订单、扣 DB 库存，用 MQ 削峰保护 DB；第四，兜底——下单失败或超时未支付要回补 Redis 库存，日终对账保证 DB 和 Redis 一致。
> 另外在入口处做分层限流和防刷，把 99% 的无效请求挡在核心逻辑之前。

## 十、追问链 · 参考答案

| 层级 | 问题 | 参考答案要点 |
| --- | --- | --- |
| L1 | 怎么防止超卖？ | 把库存前置到 Redis，用 Lua 脚本把「判断库存 + 扣减」合成一次原子操作；DB 层再用 `UPDATE ... WHERE stock > 0` 的行级 CAS 做最后一道防线。两层都用原子操作，不需要分布式锁。 |
| L2 | 为什么 GET 然后 DECR 会超卖？ | 两步之间不是原子的：并发下多个请求同时读到 `stock = 1`，全部判定通过，于是扣成负数。修法是把判断和扣减放进同一个 Lua 脚本，由 Redis 单线程整体执行，保证原子。 |
| L3 | Lua 脚本为什么能保证原子性？ | Redis 用单线程执行命令，一个 Lua 脚本作为一个整体被执行，执行期间不会被其他命令插队（相当于自带排他性）。代价是脚本必须短小，不能有耗时逻辑，否则会阻塞整个实例。 |
| L4 | Redis 扣减成功但下单失败，库存怎么办？ | 必须**回补 Redis 库存**（`INCR`），否则形成少卖。回补要幂等：只有确认订单创建失败才补，并用唯一标识防重复回补。同理，订单超时未支付也要同时回补 Redis 与 DB。 |
| L5 | 单个 SKU 全打到一个 Redis key 怎么办？ | 库存分桶：把 100 拆成 10 个 key 各存 10 个，请求按哈希/随机路由到某个桶，桶空了再换下一个。代价是可能出现「有货但没路由到」的少卖，可在活动末期合并桶缓解。 |
| L6 | 峰值再高 10 倍，瓶颈转移到哪？ | ① 网关限流成为第一瓶颈，需要集群化限流；② Redis 单实例 OPS 上限，靠分桶 + 多副本 + 客户端路由；③ MQ 堆积，靠增加分区 + 批量消费；④ DB 行锁，把库存拆到多行。 |

## 十一、误区 · 正解

| ❌ 误区 | ✅ 正解 |
| --- | --- |
| 上来就说「用 Redis 分布式锁防超卖」 | Redis 单线程执行，`DECR` / Lua 脚本已是原子操作；加锁只是把并行变串行 |
| 先 GET 判断再 DECR | 两步非原子，并发下必然超卖；合成一个 Lua 脚本 |
| 只说「用 MQ 异步」不讲可靠投递 | 要讲持久化 + confirm + 重试 + 死信 + 对账 |
| 忽略「一人一单」的幂等落点 | Redis Set 挡大部分，最终落 DB 唯一索引 `(sku_id, user_id)` |
| 预扣成功就说「秒杀成功」 | 实际是「排队中」，订单尚未创建；状态机要分开 |
| 只在 DB 层扣库存 | 瞬时 QPS 会让库存行锁排队甚至死锁超时，必须前置到 Redis |
