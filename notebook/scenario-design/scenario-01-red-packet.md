# 场景题：设计一个微信红包系统

> 场景题不是背八股，考的是**需求拆解能力 + 高并发一致性设计 + 取舍意识**。面试官真正想听的是：你先问清楚边界，然后给出一条能自洽的主链路，并主动说出方案的代价和兜底。
> 本讲按「需求澄清 → 架构 → 核心算法 → 数据模型 → 主流程 → 高并发 → 兜底 → 追问」展开。

## 一、第一步：先反问，不要上来就画架构

场景题的高分区在「提问质量」。拿到题目先花 1-2 分钟澄清，至少覆盖这四类：

| 维度 | 要问清什么 | 典型追问 |
| --- | --- | --- |
| 业务规则 | 红包类型、个数上限、金额上限 | 拼手气还是普通？一个人能抢几次？ |
| 规模 | 峰值 QPS、单群人数、红包总量 | 除夕峰值多少？单红包最多几份？ |
| 一致性 | 金额精度、能否超发/少发 | 用 double 还是分？钱扣了没领完怎么办？ |
| 时效 | 领取有效期、退回规则 | 多久没领要退？退给谁？ |

**本讲默认口径**（面试里说清楚即可，方便面试官对齐）：拼手气 + 普通红包两种；单红包最多 100 份，单份 ≤ 200 元；金额以**分**为单位；24 小时未领完退回发起人。

## 二、整体架构

```text
客户端 → 网关（限流 / 鉴权 / 幂等键） → 红包服务 → 资金服务 → 存储层
                                            ↓
                                      MQ（异步入账）
                                            ↓
                               Redis（库存 / 去重 / 延迟队列）
                                            ↓
                                  MySQL（红包 / 流水 / 账户）
```

- **红包服务**：负责红包的创建、拆分、领取分配。
- **资金服务**：负责账户扣款、入账、流水。与红包服务解耦，通过 MQ 异步联动。
- **Redis**：扛瞬时并发——库存预扣、领取去重、延迟退回。
- **MySQL**：最终落库，保证资金可审计、可回滚、可对账。

## 三、核心算法：金额怎么拆（拼手气红包）

### 3.1 二倍均值法

每一轮的随机上限 = **剩余人均金额 × 2**（左闭右开）：

```java
/**
 * 拼手气红包拆分：二倍均值法
 * @param totalFen 总金额，单位「分」
 * @param count    红包份数
 * @return 每份金额（分），顺序即领取顺序
 */
public static List<Long> split(long totalFen, int count) {
    if (totalFen < count) throw new IllegalArgumentException("每份至少 1 分");
    List<Long> result = new ArrayList<>(count);
    long remain = totalFen;
    int remainCount = count;
    ThreadLocalRandom random = ThreadLocalRandom.current();
    for (int i = 0; i < count - 1; i++) {
        long max = remain / remainCount * 2;      // 上限（不含）
        long money = random.nextLong(1, Math.max(max, 2));
        result.add(money);
        remain -= money;
        remainCount--;
    }
    result.add(remain);                             // 最后一份兜底，拿走所有剩余
    return result;
}
```

**为什么是「二倍均值」**：
- 每轮的期望 = (0 + 2×均值) / 2 = **均值** → 位置靠前靠后期望都一样，公平；
- 上限设成二倍而非全部，是为了**保证后面的人不会拿到 0**（否则前面的人可能一次抽走 99%）；
- 最后一份直接取剩余 → **天然保证总和精确等于总金额**，不需要额外的"补差"逻辑。

**其他拆法对比（加分）**：
- **线段切割法**：在 [0, total] 上取 n−1 个随机切点，段长即金额。更均匀，但要处理"切点重合导致 0 金额"和精度问题，实现比二倍均值麻烦。
- **普通红包**：`base = total / count`，余数加到最后一份上（和二倍均值一样的兜底思路）。

### 3.2 精度：必须用「分」+ long

**绝不能用 double/float 表示金额** —— 0.1 无法精确表示，累加必然出现"总额 ≠ 各份之和"，这对资金系统是致命的。统一用 `long` 存「分」，展示层再除 100。

### 3.3 预分配 vs 抢的时候再算

**微信的做法是预分配**：发红包那一刻就把每份金额算好写进明细，抢红包只是"抢一个已存在的份额"。

| 方案 | 优点 | 问题 |
| --- | --- | --- |
| 抢时实时计算 | 不用提前写明细 | 并发下要争抢"剩余金额/剩余人数"的共享状态，竞争点集中，且失败重试成本高 |
| **发时预分配（推荐）** | 抢红包退化成"原子地拿走第 k 份"，竞争点只有一个原子计数器，吞吐高 | 需要提前写 N 条明细（100 条以内完全可接受） |

## 四、数据模型

```sql
-- 红包主表
CREATE TABLE redpack (
  id            BIGINT       PRIMARY KEY,          -- 红包 ID（雪花）
  sponsor_id    BIGINT       NOT NULL,             -- 发起人
  total_fen     BIGINT       NOT NULL,             -- 总金额（分）
  total_count   INT          NOT NULL,             -- 总份数
  remaining_cnt INT          NOT NULL,             -- 剩余份数（DB 兜底）
  remaining_fen BIGINT       NOT NULL,             -- 剩余金额（DB 兜底）
  type          TINYINT      NOT NULL,             -- 1 拼手气 2 普通
  status        TINYINT      NOT NULL,             -- 0 进行中 1 已领完 2 已过期退回
  order_no      VARCHAR(64)  NOT NULL,             -- 幂等键
  expire_at     DATETIME     NOT NULL,
  created_at    DATETIME     NOT NULL,
  UNIQUE KEY uk_order_no (order_no),
  KEY idx_sponsor (sponsor_id, created_at)
);

-- 红包明细：发红包时预分配好，一行一个份额
CREATE TABLE redpack_detail (
  pack_id    BIGINT  NOT NULL,
  seq        INT     NOT NULL,                     -- 第几份，对应领取顺序
  amount_fen BIGINT  NOT NULL,
  user_id    BIGINT  NULL,                         -- NULL = 未被领取
  recv_at    DATETIME NULL,
  PRIMARY KEY (pack_id, seq),
  KEY idx_user (user_id)
);
```

**领取的核心就是一行 CAS**：

```sql
UPDATE redpack_detail
   SET user_id = ?, recv_at = NOW()
 WHERE pack_id = ? AND seq = ? AND user_id IS NULL;
-- 影响行数 = 1 才算抢到；= 0 说明这一份已被别人拿走
```

## 五、两条主流程

### 5.1 发红包

1. 参数校验（金额 ≥ 份数、份数 ≤ 100、单份 ≤ 200 元、余额充足）；
2. 以**客户端/业务订单号**做幂等（唯一索引），重复提交直接返回原红包；
3. 二倍均值拆出 N 份金额；
4. 本地事务：账户扣款 + 写流水 + 写红包主表 + 批量写明细；
5. 把每个份额 `RPUSH` 进 Redis List（或只放剩余数量计数器）；
6. 返回红包 ID，消息投递到群。

跨库时（红包库 / 账户库分离）走**可靠消息最终一致性**或 TCC，具体见 `../spring-distributed/spring-distributed-transactions.md`。

### 5.2 抢红包（高并发核心）

```text
1. 限流：网关 + 用户维度，挡掉超量请求与脚本
2. 领取去重：SADD redpack:recv:{packId} {userId} → 返回 0 直接拒绝
3. 原子分配份额：Redis List LPOP（或 INCR 序号）→ 拿到第 k 份金额
   └ LPOP 返回 nil：已抢完
4. 发 MQ（保证投递）→ 异步落库：更新 detail.user_id、账户入账、写流水
5. 返回金额给客户端（先让用户看到结果，落库异步追平）
```

**为什么不用分布式锁**：Redis 命令执行是单线程，`LPOP` / `DECR` / `INCR` 本身就是原子的，一个份额只可能被一个人拿走。加锁不会更正确，只会把并发串行化、拉低吞吐（见 `../redis/redis-04-single-thread-model.md`）。

## 六、24 小时未领完退回

| 方案 | 说明 | 适用 |
| --- | --- | --- |
| Redis ZSet 延迟队列 | score = 过期时间戳，`ZRANGEBYSCORE` 捞到期任务 | 量大、时效要求秒级 |
| MQ 定时 / 延迟消息 | RocketMQ 5.x 支持任意时间定时消息；4.x 默认 18 级最长 2h，24h 需二次投递或换方案 | 已有 MQ 基础设施 |
| XXL-JOB 定时扫描 | 扫 `status=0 AND expire_at < NOW()` 分批退回 | 量小、实现最简 |

退回同样要**幂等**：只对 `user_id IS NULL` 的明细退，且用状态机 + 唯一键防止重复退。

> ⚠️ 边界点（容易被追问）：RocketMQ 开源版 4.x 的延迟级别最多 18 级、最长 2 小时，**装不下 24 小时**。别顺口就说「用 RocketMQ 延迟消息」。

## 七、一致性与兜底（决定分数上限）

| 风险 | 表现 | 兜底 |
| --- | --- | --- |
| **超发** | 金额/份数发超了 | 库存与金额全部走 Redis 原子操作预扣，DB 层再加 `remaining_cnt >= 1` 的行级 CAS 双保险 |
| **少发** | 钱扣了但没人领完 | 过期退回 + 日终对账：`total_fen = Σ已领 + Σ已退` |
| **重复领取** | 同一人领多份 | Redis `SADD` 去重 + DB `WHERE user_id IS NULL` CAS |
| **异步落库失败** | 用户看到钱但账户没入账 | MQ 重试 + 死信队列 + 对账补偿，状态可回查 |
| **Redis 宕机** | 库存丢失 | Redis 只做「加速与去重」，DB 是权威源；恢复后按 DB 重建 |

**资金安全的底线**：任何一步都可以慢，但不能错。所有金额以分为单位、所有变更有流水、最终以对账为准。

## 八、容量估算（加分项）

- 峰值：除夕夜百万级 QPS 的领取请求（公开数据：2017 年除夕 142 亿个红包）。
- 单红包上限 100 份 → 发红包时最多写 100 行明细，压力可忽略。
- 瓶颈在**领取路径的单点竞争**：单个红包的份额分配是一个原子计数器/List，天然单点；扛住靠 Redis 单线程原子操作（十万级 OPS）+ 限流削峰。
- 热点打散思路：把一个大红包的库存拆分到多个 key（分桶），随机路由，降低单 key 竞争。

## 九、面试答题模板

**60 秒版本**（先给结论）：

> 首先澄清两点：红包类型和规模。我按「拼手气 + 单红包最多 100 份、领取 24 小时有效」来设计。
> 核心是两件事：**金额怎么拆**，和**怎么保证不超发**。
> 拆金额用二倍均值法，发红包时就预分配好，用「分」为单位避免精度问题；
> 抢红包走 Redis 原子操作分配份额 + 集合去重，扛并发，拿到份额后发 MQ 异步落库入账，最终以 DB 为准并对账。

**5 分钟版本**按下述顺序展开：需求澄清 → 架构分层 → 二倍均值算法（含代码）→ 两张表 + CAS → 发/抢两条流程 → 过期退回 → 一致性兜底。

## 十、追问链 · 参考答案

| 层级 | 问题 | 参考答案要点 |
| --- | --- | --- |
| L1 | 拼手气红包的金额怎么拆？为什么叫二倍均值？ | 每一轮在 `[1, 剩余人均 × 2)` 区间内随机取一个值。因为随机区间的上界取的是「剩余金额 ÷ 剩余人数」的**两倍**，所以叫二倍均值。这样每轮的期望值正好等于均值，先抢后抢的期望一样，天然公平。 |
| L2 | 为什么不用 double？用「分」之后最后一份怎么处理？ | double 无法精确表示 0.1 这类十进制小数，多次累加后必然出现「总额 ≠ 各份之和」，资金系统不可接受。统一用 `long` 存「分」。最后一份直接取走所有剩余金额、不参与随机，于是总和天然精确等于总金额，不需要任何补差逻辑。 |
| L3 | `UPDATE ... WHERE user_id IS NULL` 高并发下会怎样？竞争点在哪？ | 多个请求竞争**同一行**（pack_id + seq）的行锁：只有一个事务能把 `user_id` 从 NULL 改成自己、影响行数为 1，其余拿到 0 表示这一份已被抢占。竞争点集中在这一行，所以必须在 DB 之前用 Redis 原子操作挡掉绝大部分流量，只让"中签"的请求打到 DB。 |
| L4 | Redis 怎么存份额？为什么 LPOP 就够，不用加锁？ | 发红包时把预分配好的 N 个金额 `RPUSH` 进一个 List；抢红包就是 `LPOP`。Redis 单线程执行命令，`LPOP` 天然原子，一个份额只可能被一个人取走。加锁不会更正确，只会把并发串行化、拉低吞吐。 |
| L5 | 24 小时没领完怎么办？退回怎么幂等？ | 发包时投递一条 24h 延迟消息（RocketMQ 定时消息 / Redis ZSet 延迟队列 / XXL-JOB 扫表）。到期后扫描仍未领取的份额逐笔退回。幂等靠状态机：只对 `user_id IS NULL` 的明细退，退完置终态，再用唯一键防重复退。 |
| L6 | Redis 挂了库存丢了怎么办？怎么对账？ | 原则：**Redis 只是加速与去重层，DB 才是权威源**。Redis 重启后按 DB 重建库存。日常靠日终对账发现漂移：`total_fen = Σ 已领 + Σ 已退`，且 `Redis 剩余 = DB 剩余`；不一致时以 DB 为准回写 Redis。 |

## 十一、误区 · 正解

| ❌ 误区 | ✅ 正解 |
| --- | --- |
| 一上来就说「用 Redis 分布式锁」 | 用原子操作：LPOP 分配份额、SADD 去重、Lua 保证复合操作原子。锁不会更正确，只会串行化 |
| 用 double 存金额 | 用 `long` 存「分」，展示层再除 100 |
| 抢的时候实时计算金额 | 发红包时预分配，抢红包只做原子分配 |
| 只讲抢红包不讲退回 | 少发比超发更常见，退回 + 对账必须讲 |
| 幂等只靠 Redis | 最终要落 DB 唯一索引兜底 |
| 说「用 RocketMQ 延迟消息做 24h 退回」却不提版本 | 开源版 4.x 默认 18 个延迟级别、最长 2h，装不下 24h |
