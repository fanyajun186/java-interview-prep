# 场景题：点赞 / 计数系统

> 点赞题考的是「高频写 + 弱一致性要求 + 热点」。关键抓手：**计数放 Redis、幂等靠 Set/DB 唯一键、落库靠批量合并、冷热分层控内存、对账补丢失**。
> 和红包/秒杀的区别：点赞允许「少量丢失可接受 + 最终一致」，但**计数必须能自愈**。

## 一、先澄清

| 维度 | 要问清什么 |
| --- | --- |
| 规模 | 点赞 QPS、单条内容的点赞上限（如 100 万）、日活 |
| 语义 | 只有赞，还是有赞/踩？能否取消？ |
| 一致性 | 计数允许短暂不准吗？用户自己的点赞状态必须实时准吗？ |
| 展示 | 只显示总数，还是要显示「我赞过」+ 点赞列表？ |

**默认口径**：赞/取消赞、需要显示总数与「我是否赞过」、单条内容十万级点赞、允许计数最终一致。

## 二、整体架构

```text
点赞请求 → 幂等校验（Set） → Redis INCR 计数 → 变更写入 MQ
                                                    ↓
                                        定时任务 / 消费者批量落库 → MySQL
```

**核心矛盾**：点赞是超高并发的写操作，而且写的是**同一行**（某条内容的计数）。直接写 DB 会在这一行上形成严重的行锁竞争。所以计数必须前置到 Redis。

## 三、计数：Redis INCR

```text
INCR  like:count:{bizType}:{bizId}     # 点赞
DECR  like:count:{bizType}:{bizId}     # 取消赞
GET   like:count:{bizType}:{bizId}     # 展示总数
```

`INCR` / `DECR` 是原子操作，Redis 单线程执行命令，天然无并发问题——**不需要锁**。

**为什么用 String 而不是 Hash**：单 key 计数用 String 最简单，且 `INCR` 语义直接。Hash 适合「一个内容多种计数」（赞/踩/评论数）打包存储，用 `HINCRBY`，能减少 key 数量，但不能对整个 hash 设 TTL（只能对整个 key 设），需要按维度过期时得拆开。

## 四、幂等：点赞状态怎么存

**方案 A：Set**
```text
SADD like:users:{bizId} {userId}     # 返回 1 表示新增，0 表示重复 → 幂等判定
SREM like:users:{bizId} {userId}     # 取消
SISMEMBER like:users:{bizId} {userId}  # 判断是否赞过
```
缺点：只能表达「赞/未赞」，无法表达赞/踩两种状态，且大 V 的 Set 会很大（千万级成员 → 几百 MB）。

**方案 B：Hash（推荐用于赞 + 踩）**
```text
HSET like:status:{bizId} {userId} 1    # 1=赞  -1=踩  0=取消
HGET like:status:{bizId} {userId}
```
缺点：单 key 不能部分过期；超大 Hash 触发渐进式 rehash 时内存阶段性翻倍（呼应 `../redis/redis-05-internal-encoding.md`）。

**最终兜底**：DB 建唯一索引 `(biz_type, biz_id, user_id)`，Redis 去重失效时由 DB 约束挡住——**幂等必须落到持久化层**。

## 五、定时落库：合并写入

**为什么不能每次点赞都写 DB**：QPS 太高，DB 扛不住；而且同一行频繁 UPDATE 会造成行锁竞争。

**做法**：记录「计数变更流水」，定时批量合并落库：

```text
Redis: INCR like:count:{bizId}        ← 实时累加
       HINCRBY like:delta:{bizId} total 1   ← 增量（用于落库）
       ZADD like:dirty {now} {bizId}  ← 标记脏数据

定时任务（XXL-JOB 分片广播）：
   ZRANGEBYSCORE like:dirty 0 {now-5s}
   → 取出增量 delta
   → UPDATE content SET like_cnt = like_cnt + {delta} WHERE id = ?
   → 落库成功后清除 delta 与 dirty 标记
```

**关键点**：
- 增量用 `HINCRBY` 累加，落库时**取走并清零**（用 Lua 保证「读取 + 删除」原子），避免丢失或重复累加；
- 批量 UPDATE 用 `CASE WHEN` 或分批，控制单批条数；
- 落库失败不清除 dirty 标记，下一轮重试。

## 六、冷热分离

**问题**：一亿条内容都在 Redis 存计数，内存扛不住。

| 层级 | 特征 | 策略 |
| --- | --- | --- |
| **热** | 近 N 天有互动、高赞内容 | 常驻 Redis，变更频繁落库 |
| **温** | 普通历史内容 | Redis 有缓存，定时批量落库，低频访问 |
| **冷** | 长期无访问的老内容 | 从 Redis 淘汰，计数只在 DB；再访问时懒加载回 Redis |

**实现要点**：
- 用 ZSet 记录每条内容的「最近互动时间」，定时扫描把超时未互动的 key 淘汰；
- 淘汰前**必须先落库**（flush delta 再删 key），否则丢计数；
- 冷内容被访问时触发懒加载：DB 读计数 → 写回 Redis → 设 TTL；
- TTL 加随机抖动，避免集中过期。

**内存估算（打卡场景同理）**：Bitmap 一人一年 46 字节，一亿用户约 4.6 GB——这就是为什么必须冷热分离，只保留活跃用户。

## 七、热点 key

单条爆款内容的计数 key 是热点。

| 方案 | 说明 |
| --- | --- |
| **计数分片** | `like:count:{bizId}:{0..N}` 多个 key，写入随机分片，读取 `MGET` 后求和 |
| 本地缓存 | 计数在应用本地缓存 N 秒，降低 Redis 读压力（代价：短暂不一致） |
| 异步合并 | 先写本地/Redis，异步批量落库 |

**分片代价**：读取要 `MGET` 求和，稍慢；分片数固定，不能动态扩（扩容要迁移）。

## 八、一致性兜底

| 风险 | 兜底 |
| --- | --- |
| Redis 宕机，未落库的增量丢失 | 变更先写 MQ（持久化），Redis 只是加速；重启后按 MQ 重放 |
| 重复落库导致计数偏大 | 落库用 `like_cnt = like_cnt + delta` 且 delta 取走即清零，配合幂等键 |
| DB 与 Redis 长期漂移 | 日终对账：按 bizId 比对 DB 明细 `COUNT(*)` 与 Redis 计数，不一致以 DB 为准回写 |

**底线**：点赞类业务可以接受短暂不准，但**必须有对账能发现并自动修正**。

## 九、面试答题模板

**60 秒版本**：

> 先确认：是否需要显示「我赞过」和点赞列表，这决定状态存哪里。
> 方案：计数用 Redis `INCR`/`DECR`，它是原子操作，不需要加锁；点赞状态用 Set 或 Hash 存，用来做幂等——`SADD` 返回 0 就是重复点击；最终在 DB 建唯一索引兜底。
> 写入路径：实时只更新 Redis，同时把变更累到增量表里，由定时任务批量合并落库，这样把高频写削峰成低频批量写。
> 内存上做冷热分离：热内容常驻 Redis，冷内容淘汰前先落库，再访问时懒加载。
> 一致性兜底靠对账：Redis 计数与 DB 明细定期比对，不一致以 DB 为准回写。

## 十、追问链 · 参考答案

| 层级 | 问题 | 参考答案要点 |
| --- | --- | --- |
| L1 | 点赞数存哪里？为什么？ | 计数放 Redis（String + `INCR`/`DECR`），因为点赞是超高并发写同一"行"，直接写 DB 会造成严重的行锁竞争。DB 存点赞明细，用于对账与持久化。展示时优先读 Redis。 |
| L2 | `INCR` 是原子的吗？需要加锁吗？ | 原子。Redis 单线程执行命令，`INCR` 一步完成，不需要任何锁。加锁不会更正确，只会把并行变串行。 |
| L3 | 怎么防止同一个用户重复点赞？ | 用 Set：`SADD` 返回 1 表示首次点赞、0 表示重复（这就是幂等判定）；取消用 `SREM`，判断是否赞过用 `SISMEMBER`。**最终兜底必须落 DB 唯一索引** `(biz_type, biz_id, user_id)`，因为 Redis 可能宕机或 key 过期失效。 |
| L4 | 每秒十万次点赞，DB 怎么扛？ | 实时只更新 Redis；把变更累加到增量表（`HINCRBY delta`）；定时任务（XXL-JOB 分片广播）扫描脏数据，批量合并落库 `UPDATE ... SET cnt = cnt + delta`。本质是把高频随机写削峰成低频批量写。 |
| L5 | Redis 挂了，没落库的点赞数丢了怎么办？ | 变更先写 MQ（持久化），Redis 只是加速层；重启后按 MQ 重放补齐。再加日终对账：DB 明细 `COUNT(*)` vs Redis 计数，不一致以 DB 为准回写。 |
| L6 | 一亿条内容的计数全放 Redis 内存够吗？ | 不够。做冷热分离：热内容常驻 Redis；冷内容淘汰（**淘汰前必须先落库**，否则丢增量），计数只在 DB；再次访问时懒加载回 Redis 并设 TTL。 |

## 十一、误区 · 正解

| ❌ 误区 | ✅ 正解 |
| --- | --- |
| 每次点赞都写 DB | 行锁竞争 + 连接打满；实时只写 Redis，增量合并批量落库 |
| 幂等只靠 Redis Set | Redis 宕机 / key 过期就失效，必须落 DB 唯一索引兜底 |
| 只讲冷热分离，不讲淘汰前落库 | 直接删 key 会丢增量；必须先 flush delta 再淘汰 |
| 认为计数必须强一致 | 点赞是弱一致场景，但**必须有对账能自愈**，这是底线 |
