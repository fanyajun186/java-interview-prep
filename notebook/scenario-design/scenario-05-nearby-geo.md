# 场景题：附近的人 / 附近的门店

> 「附近的人」本质是**二维空间检索**：给定经纬度与半径，找出附近的点并按距离排序。考点集中在 **geohash 原理、Redis GEO 的底层实现、以及边界效应的处理**。

## 一、先澄清

| 维度 | 要问清什么 |
| --- | --- |
| 规模 | 用户量、同时在线数、查询 QPS |
| 范围 | 半径多大（500m？3km？） |
| 精度 | 距离要多准？是否需要精确排序？ |
| 频率 | 位置上报频率（这决定写压力） |
| 复杂度 | 只按距离，还是要叠加性别/兴趣等筛选？ |

**默认口径**：千万级用户、半径 3km、需要按距离排序、位置上报分钟级。

## 二、为什么不能用 MySQL 直接算

```sql
SELECT *, ST_Distance_Sphere(point(lng, lat), point(?, ?)) AS d
  FROM user_location WHERE d < 3000 ORDER BY d;
```

**问题**：`d` 是计算列，无法走索引 → 全表扫描。千万级用户下每次查询扫全表，直接打爆。

**结论**：必须用**空间索引**把二维检索降成一维范围检索。可选方案：MySQL 空间索引（R-Tree）、**Redis GEO**、Elasticsearch `geo_distance`、PostGIS。

## 三、GeoHash 原理

**核心思想**：把二维的经纬度编码成一维字符串，**前缀相同 = 地理位置邻近**。

**编码过程**（以纬度为例，经度同理）：
1. 纬度区间 `[-90, 90]` 二分，落在左半区记 0，右半区记 1；
2. 对所在子区间继续二分，重复 N 轮，得到 N 位二进制；
3. 经度同样处理得到 N 位；
4. **交错拼接**：偶数位放经度、奇数位放纬度，得到 2N 位二进制；
5. 每 5 位一组，用 base32 字符（`0123456789bcdefghjkmnpqrstuvwxyz`）编码成 1 个字符。

**长度与精度**：

| geohash 长度 | 纬度位数 | 误差 |
| --- | --- | --- |
| 1 | 2 | ±2500 km |
| 4 | 10 | ±20 km |
| 6 | 15 | ±0.6 km |
| 7 | 17 | ±150 m |
| 8 | 19 | ±38 m |

**为什么「前缀相同 = 邻近」**：geohash 本质是递归二分，前缀越长，格子越小，同一格子内的点必然距离很近。这就把「附近查询」变成了「按前缀做范围查询」。

## 四、Redis GEO

**命令**：

```text
GEOADD   geo:user 116.40 39.90 user:1001        # 上报位置（可覆盖）
GEOPOS   geo:user user:1001                      # 取坐标
GEODIST  geo:user user:1001 user:1002 km         # 算两点距离
GEOHASH  geo:user user:1001                      # 取 geohash 字符串
GEOSEARCH geo:user FROMLONLAT 116.40 39.90 BYRADIUS 3 km WITHDIST COUNT 20 ASC
```

> Redis 6.2 之前用 `GEORADIUS` / `GEORADIUSBYMEMBER`，6.2 起推荐 `GEOSEARCH`（参数更清晰）。

**底层实现（必考）**：
- GEO 类型**底层就是 ZSet**；
- member = 用户标识（如 `user:1001`）；
- **score = geohash 的 52 位整数**（经纬度 bit 交错后的整数值）；
- 查询时把「圆形范围」转成若干 geohash 网格前缀，用 `ZRANGEBYSCORE` 取候选，再算精确距离过滤 + 排序。

**边界效应（加分，常被追问）**：
- 两点物理上很近，但**恰好落在网格边界两侧** → geohash 前缀不同 → 只查中心格会漏掉；
- 解决：查询时把中心格及其 **8 个邻域格**一起查，再按真实距离过滤；
- 格子越大（geohash 越短）漏的越少但要查的邻域越多 —— 精度与查询量的权衡；
- 其他边界：高纬度地区格子实际面积变小；经度 ±180° 环绕处需要特殊处理。

**距离计算**：Redis 使用 **Haversine 公式**（球面距离），地球半径 6372797.560856 m。注意这是球体近似，非 WGS84 椭球，误差约 0.5%，业务上够用。

## 五、方案对比与选型

| 方案 | 优势 | 劣势 | 适用 |
| --- | --- | --- | --- |
| **Redis GEO** | 内存操作，延迟极低；支持距离排序 | 内存成本高；只能按距离，无法叠加复杂筛选；数据要自己维护过期 | 纯附近查询、QPS 高、数据量可控 |
| **MySQL 空间索引** | 无需引入组件；可与其他业务字段联表 | 千万级性能下降；复杂查询吃力 | 数据量小、已有 MySQL |
| **Elasticsearch** | 支持「附近 + 多条件筛选 + 分页」；天然分布式 | 运维重；写入有延迟（近实时） | 需要多条件筛选（如附近 + 评分 + 营业中） |
| **PostGIS** | 专业 GIS 能力，几何运算丰富 | 生态相对小 | GIS 强相关业务 |

**选型判断**：只按距离 → Redis GEO；要叠加筛选 → ES。

## 六、生产问题

| 问题 | 处理 |
| --- | --- |
| **GEO 数据无法自动过期** | ZSet 不支持 member 级 TTL。做法：记录上报时间戳，定时任务清理超过 N 分钟未更新的成员；或按时间窗口分 key（如 `geo:user:{hhmm}`），整个 key 设 TTL |
| **热点城市 key 过大** | 按城市/网格拆分 key（`geo:user:{cityId}`），避免单 key 千万成员 |
| **位置频繁上报的写压力** | 客户端做位移阈值过滤（移动 < 50m 不上报）；服务端合并写入 |
| **精度不够** | 调整 geohash 长度；但查询时邻域格数增加，需要压测 |
| **分页深翻** | `GEOSEARCH` 只支持 COUNT 不支持 offset；用「上次最远距离」做游标翻页 |

## 七、面试答题模板

**60 秒版本**：

> 先确认：查询半径和数据量。本质是二维空间检索，直接扫表算距离不可行。
> 方案：用 geohash 把二维经纬度编码成一维字符串，**前缀相同即邻近**，于是「附近查询」变成「前缀范围查询」。
> Redis GEO 就是这么干的：底层是 ZSet，score 存 geohash 的 52 位整数，查询时把圆形范围转成若干 geohash 前缀，ZRANGEBYSCORE 取候选再精确算距离过滤排序。
> 有个坑是**边界效应**——两点很近但落在网格边界两侧，前缀不同会被漏掉，所以要连中心格带 8 个邻域格一起查。
> 如果要叠加性别、评分等筛选，Redis GEO 就不行了，得上 Elasticsearch。

| L1 | 附近的人怎么实现？ | 本质是二维空间检索。用 geohash 把经纬度编码成一维字符串，**前缀相同即地理位置邻近**，于是「查附近的点」变成「按前缀做范围查询」。Redis GEO 直接封装了这套能力；也可选 MySQL 空间索引、ES、PostGIS。 |

## 九、误区 · 正解

| ❌ 误区 | ✅ 正解 |
| --- | --- |
| 「MySQL 经纬度加个索引就行」 | 需要**空间索引**（R-Tree），普通 B+ 树索引无法做二维检索 |
| 只说 geohash 好用不说边界效应 | 必须主动提出边界效应，并说明用 8 邻域格兜底 |
| 忽略位置数据的过期清理 | ZSet 没有 member 级 TTL，需自建时间戳清理或按窗口分 key |
| 认为 Redis GEO 能支持任意条件筛选 | 只能按距离；多条件筛选上 ES / PostGIS |
