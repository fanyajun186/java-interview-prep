# 场景题：设计一个短链系统

> 短链题看似简单，区分度在三个点：**ID 怎么发（全局唯一且不重复）**、**编码为什么是 62 进制而不是哈希**、**301 与 302 的取舍**。
> 顺带考缓存穿透防护（布隆过滤器）和高并发跳转。

## 一、先澄清

| 维度 | 要问清什么 |
| --- | --- |
| 规模 | 日生成量、跳转 QPS（读远大于写） |
| 长度 | 短码几位？是否需要自定义短码 |
| 时效 | 是否支持过期？过期后怎么处理 |
| 去重 | 同一个长链是否必须映射到同一个短链？ |
| 统计 | 是否需要点击数、来源统计（这决定 301/302） |

**默认口径**：7 位短码、读多写少（跳转 QPS 远高于生成）、需要点击统计、支持过期。

## 二、整体架构

```text
写：POST /shorten → 去重判断（Bloom）→ 发号器取 ID → 62 进制编码 → 写 DB + Redis
读：GET /{code}   → 本地缓存 → Redis → DB → 302 跳转（异步上报统计）
```

核心是**发号 + 编码**，跳转路径要尽量短（可能面对百万 QPS）。

## 三、发号器：ID 从哪来

| 方案 | 说明 | 优劣 |
| --- | --- | --- |
| **数据库自增号段** | 一次取一段（如 1000 个）缓存在本地 | 简单可靠、严格递增；单点瓶颈靠号段缓解 |
| **Snowflake** | 时间戳 + 机器位 + 序列号，本地生成 | 无网络开销、趋势递增；**需解决时钟回拨** |
| **Redis INCR** | `INCR global:id` | 简单；但每次要网络，且 Redis 持久化丢失有风险 |
| UUID | 128 位随机 | 太长、无序、索引碎片，不适合 |

**推荐**：号段模式（Leaf-segment）或 Snowflake。号段模式的优势是 ID 严格递增、DB 压力极小（每取一段才打一次 DB）；时钟回拨是 Snowflake 的硬伤，生产要么关掉 NTP 回拨，要么换号段方案。

**关键点**：ID 必须全局唯一且**不重复**——重复意味着两个长链映射到同一个短码，是 P0 故障。

## 四、编码：62 进制，不是哈希

### 4.1 为什么不用 MD5 / 哈希

| 问题 | 说明 |
| --- | --- |
| 冲突 | 哈希值可能碰撞，需要额外查重，查重本身又是并发问题 |
| 长度不可控 | MD5 有 128 位，截短后冲突率飙升 |
| 不可逆需求 | 短链不需要「从短码反推长链」，只需要一次映射，查表即可 |

### 4.2 62 进制编码

字符集 `[0-9a-zA-Z]` 共 62 个字符：

```java
private static final String ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ";
private static final int BASE = ALPHABET.length();  // 62

/** 把自增 ID 转成 62 进制短码 */
public static String encode(long id) {
    StringBuilder sb = new StringBuilder();
    do {
        sb.append(ALPHABET.charAt((int) (id % BASE)));
        id /= BASE;
    } while (id > 0);
    return sb.reverse().toString();
}
```

**为什么是 62**：只含数字与字母，**URL 安全**（不需要 percent-encoding），`-`、`_`、`+`、`/` 等在 URL 里要么有语义要么需转义。62 进制下 7 位 ≈ 3.52 万亿（62⁷），足够。

**长度计算**：`62^6 ≈ 5.68e10`，`62^7 ≈ 3.52e12`。按日生成 1 亿算，7 位可用约 96 年，留够余量。

**可选增强**：
- **防穷举 / 防遍历**：加随机盐位或洗牌算法（把 ID 与一张打乱的字符表做映射），让短码不可预测；
- **自定义短码**：需要单独一张「自定义码」表并做唯一性约束与敏感词过滤。

## 五、布隆过滤器：去重与防穿透

**两个用途**（都要说）：
1. **生成侧去重**：判断长链是否已生成过短链，避免重复占用 ID；
2. **查询侧防穿透**：查询短码前先过 Bloom，不存在的直接返回，避免打穿 DB。

**原理**：多个 hash 函数映射到一个位数组；查询时所有位都为 1 → 「可能存在」，任一位为 0 → 「一定不存在」。

**必须说清的边界**：
- **有误判率**（可能把不存在的判成存在），所以只能做「快速否定」，不能做最终判断；
- **不支持删除**：删除会影响其他元素。需要删除就用 **Counting Bloom Filter**（计数器）或 **Cuckoo Filter**；
- 误判率与位数组长度、hash 函数个数有关，可按预期数据量与容忍误判率调参；
- 布隆过滤器本身要持久化或能重建，重启后重建成本要评估。

> 加分：Redis 7 支持 Bloom Filter 模块（RedisBloom），命令 `BF.ADD` / `BF.EXISTS` / `BF.RESERVE`。

## 六、301 vs 302（高频追问）

| | 301 永久重定向 | 302 临时重定向 |
| --- | --- | --- |
| 浏览器行为 | **会缓存**跳转结果，后续直接访问长链 | 不缓存，每次都过短链服务 |
| 服务端压力 | 低（只有首次请求） | 高（每次跳转都打服务） |
| 可统计性 | ❌ 缓存后统计不到 | ✅ 每次都能统计 |
| 可变更性 | ❌ 短码一旦缓存无法改目标 | ✅ 随时改目标地址 |
| 典型场景 | 静态资源、长期不变映射 | 运营活动、需要 PV/UV 统计 |

**结论**：需要点击统计或可能需要变更目标 → **302**；纯静态、追求极限性能 → 301。
短链服务通常还要统计 PV/UV、支持运营改链接，所以 **302 是主流选择**，代价是每次跳转都要过服务端，需要 Redis 缓存挡一层。

## 七、跳转性能与缓存

```text
GET /{code}
  → 本地缓存 Caffeine（热点短码）
  → Redis（string: url:{code} → 长链）
  → DB 兜底，回写 Redis
  → 302 Location: 长链
```

- **缓存穿透**：不存在的短码 → 布隆过滤器拦截；或缓存空值 + 短 TTL。
- **缓存击穿**：热点短码过期 → 互斥重建或逻辑过期。
- **缓存雪崩**：TTL 加随机抖动。
- 统计上报走异步（MQ / 日志），不阻塞跳转。

## 八、面试答题模板

**60 秒版本**：

> 我先确认两件事：短链是否需要点击统计，以及同一个长链是否必须映射到同一个短链。
> 生成侧用**发号器**取全局唯一 ID（号段或 Snowflake），再转成 **62 进制**做短码——不用哈希是因为有冲突、长度不可控。7 位 62 进制有 3.5 万亿空间，足够。
> 映射关系存 DB，Redis 缓存挡读流量。
> 跳转用 **302 而不是 301**：301 会被浏览器缓存，后续请求不再经过服务端，就统计不到点击了；代价是每次跳转都要过服务端，所以用 Redis + 本地缓存扛。
> 防穿透用布隆过滤器，它有误判率、不支持删除，所以只做快速否定，最终判断仍要查库。

## 九、追问链 · 参考答案

| 层级 | 问题 | 参考答案要点 |
| --- | --- | --- |
| L1 | 短码怎么生成？ | 发号器取全局唯一自增 ID（号段模式或 Snowflake），再把 ID 转成 62 进制字符串作为短码。短码 → 长链的映射存 DB，Redis 缓存挡读流量。 |
| L2 | 为什么用发号器 + 62 进制，而不是 MD5？ | 哈希有三个问题：① 可能冲突，需要额外查重，而查重本身又是并发问题；② 长度不可控，MD5 有 128 位，截到 7 位冲突率飙升；③ 短链只需要一次映射关系，查表即可，根本用不到摘要/可逆能力。发号器方案零冲突、长度可控、容量可精确估算。 |
| L3 | 7 位 62 进制能表示多少？怎么算的？ | `62⁷ ≈ 3.52 × 10¹²`，约 3.5 万亿；对照 `62⁶ ≈ 5.68 × 10¹⁰`。按日生成 1 亿条算，7 位可用约 96 年，余量充足。 |
| L4 | 301 和 302 怎么选？对统计有什么影响？ | 301 是**永久**重定向，浏览器会缓存跳转结果，后续请求不再经过短链服务 → 统计不到点击；302 是**临时**重定向，每次都过服务端 → 可统计、可随时改目标。主流短链服务要统计 PV/UV，所以用 302；代价是每次跳转都打服务端，需用 Redis + 本地缓存扛。 |
| L5 | 布隆过滤器有什么缺点？怎么支持删除？ | 两个硬约束：① **有误判率**——可能把「不存在」判成「存在」，所以只能做快速否定，最终判断仍要查库；② **不支持删除**——多个元素共享位，删一个会影响其他。要支持删除换成 Counting Bloom Filter（计数器）或 Cuckoo Filter。 |
| L6 | 短码被遍历穷举怎么防？ | 三层防护：① 让短码不可预测——加随机盐位，或用洗牌算法打乱字符表后再编码；② 限流——按 IP / 用户维度限制访问频率；③ 内容治理——对跳转目标做安全检测，违规立即下线。 |

## 十、误区 · 正解

| ❌ 误区 | ✅ 正解 |
| --- | --- |
| 用 MD5 取前 7 位当短码 | 冲突率高且必须额外查重；自增 ID + 62 进制零冲突 |
| 只说布隆过滤器优点 | 必须说清**误判率**与**不可删除**，并给出 Counting Bloom / Cuckoo Filter 解法 |
| 认为 302 更好却不解释代价 | 302 每次跳转都打服务端，需要缓存层扛；不需要统计才用 301 |
| 忽略短码可预测性 | 自增 ID 直接编码可被遍历，需随机化或洗牌 |
