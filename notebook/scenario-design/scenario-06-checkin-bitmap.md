# 场景题：签到打卡与缺卡查询（Redis Bitmap）

> 打卡题是 **Bitmap 的最佳舞台**：365 天打卡只要 46 字节/人。考点是：**offset 怎么设计、用哪些命令、以及 SETBIT 拉伸和大 key 的坑**。
> 面试官真正想听的：你能算出为什么用 Bitmap，以及它什么情况下会失效。

## 一、先澄清

| 维度 | 要问清什么 |
| --- | --- |
| 粒度 | 按天打卡？一天多次只记一次？ |
| 周期 | 按月 / 按年统计？是否有连续打卡奖励？ |
| 查询 | 查某天是否打卡？查当月打卡天数？查连续天数？**查缺卡日**？ |
| 补卡 | 是否支持补卡？补卡是否影响「连续」判定？ |
| 规模 | 用户量、日活（决定内存与是否需要冷热分离） |

**默认口径**：按天打卡、按月分片、需要「连续打卡天数 + 首次缺卡日 + 月打卡总数」、支持补卡。

## 二、方案对比：为什么是 Bitmap

| 方案 | 存储/人/年 | 问题 |
| --- | --- | --- |
| MySQL 一行一天 | 365 行 × ~50 字节 ≈ 18 KB | 行数爆炸，索引膨胀，统计要聚合 |
| Redis Set（每天一个 member） | 365 个字符串 ≈ 10 KB+ | 成员越多编码越重，内存远大于位图 |
| **Redis Bitmap** | 365 bit ≈ **46 字节** | 几乎只有优点（见下方边界） |

**结论**：打卡是典型的「大量布尔值」场景，一个 bit 表示一个状态，Bitmap 是空间最优解。

## 三、数据结构设计

```text
key    = sign:{userId}:{yyyyMM}      # 按月分片，如 sign:1001:202610
offset = 当月的第几天 - 1            # 1 号 → 0，31 号 → 30
value  = 0 未打卡 / 1 已打卡
```

**为什么要按月分片**：
- 避免单个 key 过大（一年 46 字节看着小，但一亿用户就是 4.6 GB）；
- `SETBIT` 在 offset 很大时会**一次性拉伸字符串**并分配内存，首次设置大 offset 会造成明显卡顿；按月分片后单 key 最大 4 字节，无此问题；
- 便于按 key 设 TTL 归档历史月份。

## 四、核心命令

```text
# 打卡（第 15 天）
SETBIT sign:1001:202610 14 1

# 查某天是否打卡
GETBIT sign:1001:202610 14

# 统计当月打卡总天数
BITCOUNT sign:1001:202610
# 统计某段区间（注意 start/end 单位是字节，不是 bit）
BITCOUNT sign:1001:202610 0 3

# 查首次缺卡日：找第一个值为 0 的 bit
BITPOS sign:1001:202610 0
# 查首次打卡日
BITPOS sign:1001:202610 1

# 取当月所有位为一个无符号整数（用于算连续天数）
BITFIELD sign:1001:202610 GET u31 0
```

## 五、连续打卡天数怎么算

```java
/**
 * 计算「截至今天」的连续打卡天数
 * @param v    BITFIELD GET u{len} 0 取回的整数
 * @param len  当月天数（28/29/30/31）
 * @param today 今天是几号（1-based）
 */
public static int continuousDays(long v, int len, int today) {
    int count = 0;
    for (int d = today; d >= 1; d--) {
        // Redis 位序是 MSB-first：第 d 天对应整数中第 (len - d) 位
        if (((v >>> (len - d)) & 1) == 1) {
            count++;
        } else {
            break;
        }
    }
    return count;
}
```

> ⚠️ 位序坑：Redis 里 `SETBIT key 0` 设置的是第 0 字节的**最高位**，与「第 0 位是最低位」的直觉相反。上面的 `len - d` 就是为此做的换算。**写完务必自测**（`SETBIT` 第 1 天，看 `GET u31 0` 是不是 `2^30`）。

**跨月连续**：把上月最后一段和本月拼起来算——取上月的 `u31` 值，从月末往回数连续的 1，再加上本月到今天的连续 1。

## 六、补卡

补卡就是在对应 offset 再 `SETBIT` 一次，天然幂等：

```text
SETBIT sign:1001:202610 9 1     # 补 10 号的卡
```

**业务上要注意**：补卡是否计入「连续」取决于规则。常见做法是补卡可计入总数，但连续天数按「补卡日期」而非「原日期」计算，或限制每月补卡次数——这属于业务规则，面试时主动提一句「这里有产品取舍」即可。

## 七、边界与坑（高分区）

| 坑 | 说明 | 应对 |
| --- | --- | --- |
| **SETBIT 拉伸** | 大 offset 一次性分配内存，主线程卡顿 | 按月分片 key，单 key 控制在几字节 |
| **BITCOUNT 大 key** | 复杂度 O(n)，超大 key 会阻塞 | 同上分片；或用 `BITFIELD` 分段统计 |
| **单位陷阱** | `BITCOUNT` / `BITPOS` 的 start/end 参数是**字节**不是 bit | 计算偏移时先除以 8 |
| **月份天数不同** | 2 月可能 28/29，4/6/9/11 月 30 天 | 取当月实际天数，别硬编码 31 |
| **时区** | UTC vs 本地时区会导致「今天」判定错位 | 服务端统一时区，或按用户时区分 key |
| **持久化风险** | Redis 宕机会丢未落库的打卡记录 | 开启 AOF（everysec）；关键打卡异步落 DB；对账修复 |
| **冷用户内存** | 一亿用户 ≈ 4.6 GB | 冷热分离：只保留活跃用户，历史月归档到 DB |

## 八、与 DB 的协同

```text
写：SETBIT（实时） → 发 MQ → 异步落库（sign_record 明细表）
读：优先 Redis，miss 则从 DB 明细重建 bitmap
兜底：日终对账 —— DB 明细 COUNT(*) vs Redis BITCOUNT，不一致以 DB 为准回写
```

**为什么要落 DB**：Redis 是内存，打卡记录属于用户资产（影响奖励发放），必须有持久化凭证，且便于追溯与审计。

## 九、面试答题模板

**60 秒版本**：

> 先确认两点：是否支持补卡、需要统计哪些维度（连续天数 / 缺卡日 / 总数）。
> 方案用 **Redis Bitmap**：key 设计成 `sign:{userId}:{yyyyMM}`，按月分片；offset 是「当月的第几天 − 1」，value 是 0/1 表示是否打卡。这样一人一年只用 365 bit，约 46 字节，空间极省。
> 几个核心命令：`SETBIT` 打卡、`GETBIT` 查某天、`BITCOUNT` 统计总数、`BITPOS key 0` 直接找**第一个缺卡日**。
> 坑有三个：一是 `SETBIT` 到大 offset 会一次性拉伸字符串导致卡顿，所以必须按月分片；二是 `BITCOUNT`/`BITPOS` 的区间参数是**字节**不是 bit；三是 Redis 位序是 MSB-first，和直觉相反，自己算连续天数时要换算。
> Redis 只做加速，打卡记录要异步落 DB 并对账，因为涉及奖励发放，不能只放在内存里。

## 十、追问链 · 参考答案

| 层级 | 问题 | 参考答案要点 |
| --- | --- | --- |
| L1 | 一年的打卡记录怎么存最省？ | 用 Redis **Bitmap**：一天一个 bit，一年 365 bit ≈ **46 字节/人**。对照：DB 每天一行约 18 KB/年，Redis Set 存日期字符串 10 KB+/年。打卡是典型的"大量布尔值"场景，一个 bit 一个状态，空间最优。 |
| L2 | Bitmap 的 key 和 offset 怎么设计？ | `key = sign:{userId}:{yyyyMM}` **按月分片**；`offset = 当月第几天 − 1`（1 号 → 0）。按月分片的三个理由：控制单 key 大小、`SETBIT` 大 offset 会一次性拉伸字符串造成卡顿、便于对整个 key 设 TTL 归档历史月份。 |
| L3 | 怎么查「第一次缺卡是哪天」？ | 一条 `BITPOS key 0` 直接返回第一个值为 0 的 bit 位置，加 1 就是缺卡日期。这是 Bitmap 在打卡场景最漂亮的一手，完全不需要遍历。 |
| L4 | 怎么算连续打卡天数？ | `BITFIELD key GET u{当月天数} 0` 取回当月所有位组成的一个无符号整数，再从今天往回数连续的 1。**坑**：Redis 位序是 **MSB-first**（offset 0 是第 0 字节最高位），第 d 天对应整数中第 `len − d` 位，与直觉相反，写完务必自测。跨月时拼接上月末段与本月段。 |
| L5 | `SETBIT` 一个很大的 offset 会怎样？ | 会一次性拉伸字符串并分配内存，主线程出现明显卡顿（若按年存、offset 取到第 365 天也会瞬间分配 46 字节，量级尚可，但按"绝对日期"当 offset 就是几 MB 级别）。按月分片把单 key 控制在几字节；另外 `BITCOUNT` 是 O(n)，大 key 同样要避免。 |
| L6 | 一亿用户全放 Redis 内存够吗？ | 约 **4.6 GB**（365 bit/人），太大。做法：只保留**活跃用户当月**的 bitmap，历史月归档到 DB 并对 key 设 TTL；需要统计年度数据时再按需加载合并。这就是冷热分离在打卡场景的落点。 |

## 十一、误区 · 正解

| ❌ 误区 | ✅ 正解 |
| --- | --- |
| 把 offset 设计成真实日期（如 20261015） | 会直接拉伸到几 MB；用「当月第几天 − 1」并按月分 key |
| 用 Set 存每天打卡 | 内存比 Bitmap 大几十倍，Set 成员越多编码越重 |
| 认为 `BITCOUNT` / `BITPOS` 的区间参数是 bit | 单位是**字节**，计算偏移时要先除以 8 |
| 忽略时区 | 跨天判定会错位；服务端统一时区，或按用户时区分 key |
| 只用 Redis 不落库 | 打卡影响奖励发放，属用户资产，必须有持久化凭证与对账 |
